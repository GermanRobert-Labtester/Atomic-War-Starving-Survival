## 1. Objective and bounded outcome

Replace one placeholder stress input with a measured current environmental projection, route one legal repair command through current inventory and skill/duty authorities, and show component condition with actual costs and effects. Extend to further components only after the first outcome is observed end to end.

**Current state:** ShelterMaintenanceSystem, component catalog, host, registered save section and day tick are live. Main.TickShelterMaintenance passes GetWeatherStressMultiplier and GetRadiationStressMultiplier, both currently return constant 1.0 with TODO comments. Host exposes PerformMaintenance and warning/failure projections; the inspected Main file has no player command or panel binding for maintenance, so repair may remain a host-only route. A component warning does not by itself prove power, water or facility degradation reaches the owning systems.

**Non-goals:** No second weather/radiation state, free repairs, condition copied into power/water stores, failure caused solely by a UI label, or invented technician skill.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

## 3. Current contract and collision firewall

- **Evidence or explicit premise:** ShelterMaintenanceHostSession loads validated shelter_components.json and saves shelter_maintenance.
- **Evidence or explicit premise:** Main.TickShelterMaintenance is live, but both weather and radiation stress helpers return constant 1.0.
- **Evidence or explicit premise:** Host PerformMaintenance exists with component/action/skill/day inputs.
- **Evidence or explicit premise:** No production Main player repair command was found in the inspected maintenance partial.
- **Evidence or explicit premise:** Warning and failed component lists are Core read models; downstream facility effects require owner checks.
- **Evidence or explicit premise:** Actual resource debit and worker skill remain separate canonical authorities.

### Condition is a fact; repair is a transaction

The maintenance engine already advances component condition each campaign day and persists it. The current host, however, gives it constant weather and radiation multipliers. Any plan that advertises environment-sensitive wear as already live would be false. Select one actual environmental signal whose source system exposes a stable, bounded readout; document units and snapshot timing. The component owner uses that readout for its degradation formula, but does not take ownership of weather or radiation. If no suitable public read API exists, keep the input at neutral and name the dependency instead of scraping UI text.

`PerformMaintenance` is not automatically a player route. The host must check an actual built component, allowed repair action, inventory stock, worker availability and skill before committing costs and condition change. The resource transaction should avoid consuming materials when the repair refuses, and replay after save should not consume twice. If the current Core repair method mutates before an external inventory debit can be guaranteed, define an owner-safe preflight/commit handshake. Component failure effects on power, water or rooms require an explicit consumer contract. The maintenance UI can always show warning condition, but it must not claim a pump stopped unless the pump owner accepted the state.

Wear prose should be diagnostic and physically specific: a valve sticks, a gasket leaks, an inspection tag has been amended. Each line must map to a condition band and a known component ID. Repair copy should state the action and recorded outcome without inventing spare parts or a named worker.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 7. State, save and migration

Inspect `src/Host/ShelterMaintenanceHostSession.cs` and the registry for the named concern; absence of a section is a decision gate, not permission to invent one. Write down exact DTO version, constructor baseline, capture point, restore point, and dirty flag. If a new mutable field is genuinely required, version the existing owner DTO and prove migration from the preceding schema. Never equate a panel cache with campaign state.

The restore sequence is: catalog validated; source state restored; destination state restored; adapters bound; pending effects reconciled once; UI bound; day processing resumes. A new campaign starts with an explicit empty/default state. A legacy save without the field takes that same baseline without inventing past events. Unknown future schema versions must fail or degrade according to the existing save contract, with a visible diagnostic. Corrupt single records must not silently reset an entire unrelated section.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.

## 9. Player commands and UI

Inspect the current route to `src/UI/ShelterPanel.cs` and its bind/open/close methods. Expose only commands backed by an existing Core method or a specifically planned method in the named owner. The panel should show source state, currently legal action, expected cost, blocker, committed outcome, and uncertainty where the game cannot know more. Refresh on authoritative state change and after restore; unbind subscriptions on close/disposal. Preserve keyboard/controller back and readable contrast.
