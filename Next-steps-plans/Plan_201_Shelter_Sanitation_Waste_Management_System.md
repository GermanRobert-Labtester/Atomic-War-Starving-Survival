## 1. Objective and bounded outcome

Deepen real waste-state and cleaning feedback, validate a single downstream medical or room consequence from current hygiene projection, and add facility/incident prose only where the sanitation owner can produce the condition. Preserve Plan 210 room, power and compost wiring.

**Current state:** SanitationSystem is already live with room waste, hygiene bands, daily population feed, cleaning, compost, facility catalog, power provider, Main save and SanitationPanel. Plan 210 provides the active host, room registration from shelter_rooms.json, room power feed, and compost delivery into canonical inventory. Plan 201 must be treated as additional content/consumer depth on this owner, not a new SanitationSystem. Main.SaveSanitation currently captures the section; any dirty-flag semantics should be checked against the current save orchestrator before editing.

**Non-goals:** No duplicate waste counter, direct disease from prose, free compost on panel refresh, room identity invented from text, or second sanitation save section.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

### Hygiene describes a room; illness remains a medical event

The older Plan 201 premise says no sanitation system exists. Current code disproves that: SanitationSystem tracks room burden and hygiene, accepts cleaning, advances with population, manages facility power and compost, and persists through the `sanitation` section. The source of truth for room IDs remains shelter_rooms.json; Main registers rooms by tags and binds power state at the facility tick. The first residual package should therefore select one output of this live system—such as a room's pathogen exposure modifier—and determine whether a current medical exposure calculation consumes it. If not, show hygiene as a risk projection and identify the missing medical handoff rather than spawning disease from a sanitation panel.

Cleaning is a transaction requiring workers, skill, priority and day. The panel can request a cleaning action only if current duty/roster and resource contracts allow it. A cleaning result can update room burden, but it should not directly edit morale or health. Compost output is already delivered to inventory by OnCompostReady. Verify repeated callbacks, save between production and delivery, and failed inventory addition before adding more compost prose. Avoid writing that a batch was stored until inventory accepted it.

Sanitation prose should be practical and restrained: a blocked drain, a sharp disinfectant smell, a shift note about gloves running low. The line's trigger is a real room/facility state band. A “clean” label must not imply sterile conditions; a warning should show which room and measured burden produced it. Plan 210 remains the integrated authority, and this plan's residual work is content and a bounded consumer check.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.

## Architecture close and promotion handoff

The integration architecture for **Sanitation** is therefore: authored JSON `sanitation_facilities.json and shelter_rooms.json` → `SanitationSystem` → `SanitationHostSession, Main.Sanitation.cs, SanitationPanel` → existing save owner `sanitation` → a read-only Godot projection. This is the entire intended direction of dependency. A consumer may ask the owner for a fact; it may not mutate the owner's private copy or introduce a parallel clock, resource, outcome, or ledger. The phase-0 audit must replace the illustrative framework with exact current signatures and record any contrary source evidence.

**Promotion packet:** one chosen card ID; desired player outcome and explicit non-goals; current file:line premise; exact claimed paths; authoritative command and state owner; catalog row IDs; save migration classification; day order; panel route; 3–6 observable acceptance criteria; focused verification command. A foreman or named integrator may promote that packet. This document alone does not promote it.

**Polishing gate:** read every new player-facing line aloud for the restrained ASHFALL register, remove verdicts on the player's morality, remove unsupported reward language, align naming with live IDs, and reject any card that merely repeats a neighboring card without a distinct state or failure mode. Preserve historical closeout claims as dated claims, not as evidence of today's runtime.
