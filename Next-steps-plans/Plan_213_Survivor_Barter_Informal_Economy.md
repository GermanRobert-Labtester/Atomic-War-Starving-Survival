# Plan 213 — Informal Barter Economy — Transactional Personal Trade Integration

## PFGL Codex Luna 6 execution revision — 2026-09-25

**Verified boundary:** DEC-198 and the pure `SurvivorBarterSystem`, `barter_rules.json`, and seven focused tests exist. No production host constructs the system. This concern is survivor-to-survivor informal trade; `ShelterBarterSystem` remains a separate caravan/airlock trade authority. `AcceptOffer` currently validates through optional `HasPersonalItem` and calls a `void TransferPersonalItem` hook, so it cannot prove inventory settlement succeeded atomically. `PersonalBelongingsSystem` stores one-per-item-definition claim metadata and expressly does not own stack quantity or physical item transfer.

**Bounded implementation:** host the existing offer/favor/reputation authority and add a transaction-safe settlement seam that delegates stack movement to the canonical inventory transaction API. An offer can settle only after the complete reciprocal bill is quoted and committed; failed/partial commits leave offer status, pair reputation, personal claim metadata, and inventory unchanged. Do not treat item-definition IDs as unique physical instance IDs. Do not expose offer acceptance before this contract is verified. Persist barter negotiation separately from external trade traffic.

**Acceptance:** offers, rejects, favors, disputes, day expiry, and pair reputation survive capture/restore; one successful exchange moves both sides' stacks once; insufficient stock, stale inventory, duplicate item lines, and failed commit do not create a settled trade; no UI callback mutates reputation or creates items. The route may be added after the host settlement API passes focused tests.

## 1. Objective and bounded outcome

Integrate one survivor-to-survivor gift or offer using a transaction-safe possession command from the current personal belongings owner, then wire one saved offer lifecycle and a truthful social player route. Resolve the transaction boundary before exposing AcceptOffer.

### Transaction and custody dossier

The signed DEC-198 Core model owns negotiation state, not physical items. Its current `AcceptOffer` validates possession through an optional predicate, invokes an optional void transfer callback for each item, then marks an offer Accepted, records a trade, creates favors, and increases trust. That sequence is not an atomic settlement contract when a transfer can fail after another transfer or when callbacks are absent. An implementation plan must begin with a narrowly claimed transaction seam in PersonalBelongingsSystem or Inventory that can validate and commit both legs as a single result. The barter owner should only finalize its offer after a successful settlement result. If this cannot be achieved without changing the owner, item trade remains blocked; favor-only offers may be a separate, lower-risk slice after author identity and duty completion rules are established.

The existing airlock ShelterBarterSystem, MarketSystem barter demo, and BlackMarketSystem are not personal informal exchange owners. Do not reuse their panels, save records, stock or currencies. Pairwise trust in SurvivorBarterSystem is its own negotiation reputation. If a signed relationship effect is desired, the social coordinator must accept an attributed delta once; a callback alone is not permission to mutate relationship records twice.

The three rules in `barter_rules.json` are policy parameters, not prices. Current Core has statuses Countered and Settled in the enum but no public counter/settle command in this sweep. UI must show only actual states and avoid a counter-offer button until the command and migration rules exist. Saved offers reference live survivor and personal item IDs; restore must tolerate missing participants by marking an offer unavailable without fabricating transfers.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.
