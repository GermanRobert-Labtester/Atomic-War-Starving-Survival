### Source alert and response custody dossier

An emergency alert is a readout and response coordinator for an incident owned elsewhere. The first slice should select a real producer, such as a verified fire, defense breach or power failure, with stable incident ID, affected zone, actual day/hour and clear termination event. `RaiseAlert` currently lacks source event ID and accepts unknown type IDs with default values. The Core owner must gain or be wrapped by a durable keyed admission rule before the host subscribes to repeated producer callbacks. A second callback for the same incident should update or preserve the alert, not make `alert_2`. An unknown catalog type should produce a blocked diagnostic in a production path.

Hourly escalation is stateful and currently independent of the campaign clock. Bind `TickHour` only to the existing hour owner and save the alert section before a UI readout claims remaining time. If the campaign only ticks days in the relevant mode, decide whether an hour-level alert is supported or use a named day-boundary translation; never call TickHour in a panel refresh. Acknowledgement means the player saw/accepted responsibility; it must not magically repair an incident. Resolution follows the source owner closing the fire, breach or medical danger. A protocol can request evacuation through the current duty/room owner, but `ActivateProtocol` alone is just a record.

The panel needs a ranked alert list, source and zone, remaining time, legal response, acknowledgement, resolution history and text alternative to audio/color. Cue identity belongs to the existing audio catalog; an audio cue should play once per raise/escalation transition and respect user volume/accessibility settings. Warning prose is functional: it should identify what is known, the affected zone and a concrete next step. It should not claim casualties or containment before a producer confirms them.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

### Save and lifecycle order

The existing section is the only durable owner listed in the plan. Validate the catalog, create or select the one owning Core instance, restore that section, then bind event adapters and UI. Capture after an accepted command and before dirty flags are cleared. When two existing sections change in one journey, document capture order and the recovery behavior for a save between them. Restore must not replay a player reward, resource transfer, relationship delta or notification. An old save missing the section gets the documented empty or seeded baseline, not fabricated historical actions. A future schema uses the current codec rejection rule and a corrupt envelope must not masquerade as a valid empty state.

### Deterministic day and event order

Use `_simDay` or the campaign day coordinator argument, never a literal UI day or wall-clock clock. A day tick runs once per accepted campaign day and sorts unstable source collections by stable ID before effects. A read-only projection is pure; reopening a panel cannot fire a Core command. For each subscription, name where it is bound, when it is unbound, and whether restore can emit it. If the source event is retried, an owner-persisted key or already-committed state prevents the second effect; a process-local flag is insufficient.

### Player surface and accessibility

Show current state, legal action, cost and consequence, and precise blocker in the same view. Preserve keyboard/controller back and focus after an action or refresh. Display long authored text with wrapping and scroll, preserve empty states, and keep private/undiscovered content gated. A card never shows a morale, skill, resource, room or map outcome unless the matching authority has committed it. Bounded visible rows may paginate without truncating saved records.

### Reviewable phases and rollback

Phase 0 records current source/data/host evidence and an exact path claim. Phase 1 seals the owning Core command and one refusal. Phase 2 validates catalog IDs and references. Phase 3 wires save and day through current ownership. Phase 4 exposes one player route. Phase 5 adds authored content only after that route can consume it. Focused tests are selected under TEST_POLICY.md when implementation begins. A failed phase can be reverted without discarding other owner state; incomplete effects are reported as blocked, not quietly simulated in UI.
