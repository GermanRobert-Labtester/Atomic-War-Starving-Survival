# Plan 169 — Audio Accessibility & Mix Legibility — Critical-Cue Visual Equivalence, Dynamic Range Ducking, Mix Presets, and Host Bus Telemetry

## 1. Objective and bounded outcome
Deliver the canonical, authoritative implementation and integration architecture for **Plan 169 (Audio Accessibility & Mix Legibility)**. This specification establishes the immutable system contracts, host wiring, data schemas, persistence boundaries, deterministic day semantics, failure handling, UI adapters, and verification protocols required to operate within the ASHFALL runtime without introducing parallel authority, architectural fragmentation, or save corruption.
**Current production state:** The system is governed by `DEC-161 (signed 2026-09-21), DEC-319 (signed 2026-09-24)` and anchored in Master Expansion Authority `Volumes 1-57 Master Expansion Authority (Part III C17 UI/Accessibility, C8 Audio/Radio, v1.0 Part 8.4 Presentation Standards)` under subsystem cluster `C17 Host surface and UI / C8 Radio and information / C16 Progression and meta`. Pure domain logic is anchored in `Assets/Ashfall.Core/Audio/AudioAccessibilityCoordinator.cs`. Host composition routes through `src/Host/AudioAccessibilityHostSession.cs` and `src/Main.AudioAccessibility.cs`. Data definitions are authored strictly in `Assets/StreamingAssets/Data/audio_accessibility_cues.json`. Persistence and profile custody adhere strictly to `UserSettingsData (VisualAudioAlerts, AudioMixPreset via UserSettingsStore; zero campaign save pollution)`. Comprehensive verification is gated via `Ashfall.Core.Tests/Audio/Plan169AudioAccessibilityIntegrationTests.cs`.
### Non-goals and strict boundaries:
1. **Zero engine leaks:** Pure Core domain logic in `Assets/Ashfall.Core/` must never reference Godot, UnityEngine, or engine serialization APIs.
2. **No parallel state stores:** Do not create auxiliary ledgers, shadow registries, or independent state stores that bypass the canonical save section or settings authority.
3. **JSON authority:** Authored configurations reside exclusively in `Assets/StreamingAssets/Data/` under validated schemas. Runtime code must not hardcode gameplay authority tables.
4. **Deterministic execution:** All calculations, timers, random rolls, and state transitions must be strictly reproducible using seeded random streams (`ISeededRng`). Wall-clock time or unseeded `System.Random` is strictly prohibited.

To ensure total system stability, Plan 169 operates behind a rigid collision firewall. The subsystem is strictly partitioned from competing domains and adheres to these core invariants:

## 7. State, save and migration
State persistence is strictly controlled through versioned Data Transfer Objects (DTOs) adhering to `UserSettingsData (VisualAudioAlerts, AudioMixPreset via UserSettingsStore; zero campaign save pollution)`. The state envelope records schema version, timestamp/day, and immutable record lists. Migrations between schema versions must be explicit, unit-tested, and idempotent.

## 8. Event, day and failure semantics
Events represent immutable facts that have already occurred. Handlers must be idempotent; receiving an identical event multiple times must not compound mutations. Daily processing hooks into `CampaignDayCoordinator.OnDayAdvanced`.

## 9. Player commands and UI
UI surfaces function strictly as projection layers. Panels query current read-models from host sessions and format numbers/labels using localized tokens. Player input translates into typed command DTOs passed to host sessions.
