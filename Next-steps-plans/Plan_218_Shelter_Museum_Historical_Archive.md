# Plan 218 — Shelter Museum Archive — Host, Projection, and Save Custody

## PFGL Codex Luna 6 execution revision — 2026-09-25

**Verified boundary:** DEC-203 is signed. `ShelterMuseumSystem`, `museum_collection_templates.json`, capture/restore, exhibition/visit rules, and seven focused tests already exist. No production host constructs the museum. `CulturalArchiveVaultSystem` owns the distinct `cultural_archives` save section; it must not silently absorb museum state. `DonateFromTemplate` creates a museum record from a template ID, not a physical inventory transfer. `VisitMuseum` mutates visit counts on every call, so it must never be invoked by a read-only panel bind/refresh.

**Bounded implementation:** add one host/save/day owner and a museum projection route. The first player surface may inspect artifacts, curator, events, and exhibitions; it must not enable donation from physical inventory until the inventory transaction and museum admission can commit as one coherent operation. Visits must be explicit once-per-visit commands, with any morale delta applied by the canonical Needs owner and no gain on panel refresh. Keep the museum save key separate from external communications and the cultural vault.

**Acceptance:** restore reproduces curator, artifacts, events, exhibitions, and counts; expiry closes an exhibition once; a read-only refresh never increments visitors; donation is unavailable unless physical item custody is transaction-safe; morale is applied exactly once through Needs. No synthetic inventory removal or second archive ledger.

## 1. Objective and bounded outcome

Bind one museum instance to the campaign culture lifetime, show a real donated artifact and exhibition projection, and save/restore visitor and curator state through an approved existing cultural owner. Guard physical item custody before enabling donations.

**Current state:** DEC-203 SIGNED: pure Core museum with six artifact template rows covering eight artifact types and seven themes. No src construction or save binding found. CulturalArchiveVaultSystem already has its own cultural_archives section, so museum state needs an approved additive custody path, not an assumed separate archive.

**Non-goals:** No duplicate physical inventory, synthetic prewar provenance, automatic confiscation of keepsakes, unbounded visit farming, or second cultural archive store.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

## 3. Current contract and collision firewall

- **Evidence or explicit premise:** ShelterMuseumSystem exposes LoadCatalog, GetTemplate, AppointCurator, DonateArtifact, DonateFromTemplate, CurateExhibition, CloseExhibition, VisitMuseum, TickDay, GetHistoricalSignificanceScore and CaptureState/RestoreState.
- **Evidence or explicit premise:** DonateArtifact and DonateFromTemplate create a museum record without consuming or reserving an Inventory item. A player donation route needs a canonical item transaction and stable linkage before exposing the button.
- **Evidence or explicit premise:** CurateExhibition accepts artifact IDs and marks found IDs on display, but the shown method does not reject unknown IDs; host validation or a bounded Core invariant change is required.
- **Evidence or explicit premise:** VisitMuseum adds total visitors and morale yield on each call; an unrestricted panel click could farm morale. A day-level visit policy and Needs attribution must be owned and persisted.
- **Evidence or explicit premise:** The existing CulturalArchiveVaultSystem uses cultural_archives save custody, while museum has no src host; embedding is a proposed decision, not a current fact.
- **Evidence or explicit premise:** The JSON has six artifact template rows and seven theme strings; artifact type enum has eight values. These are distinct counts and must not be advertised as eight authored artifacts.

### Museum integration and provenance dossier

The signed museum Core system stores artifact records, exhibitions, curator appointment, visit counts, event history and next IDs. None of that proves physical item custody. `DonateFromTemplate` uses the template ID as its `ItemId`, which may be a museum template rather than a canonical inventory item. A player donation flow must first resolve one real physical item or explicitly make the template a nonphysical historical record; it must never decrease stock through museum state alone. If the item is a personal keepsake, PersonalBelongingsSystem must authorize the owner transfer or decline it. A historical story is authored content, not proof that an item was ever acquired.

The current culture vault and archive desk already own other archival functions. Integrating the museum should add a read model and, if approved, an additive museum field under cultural_archives. The save owner must capture museum and vault state consistently so an exhibition cannot point at an artifact that disappears after reload. If that aggregate cannot own museum state under the current decision register, obtain an explicit new save decision before implementation; do not silently introduce museum_save.json.

`VisitMuseum` returns a morale number but does not apply Needs. To expose visits as a player command, define who can visit, how often, how a visit is keyed by survivor and day, and when the Needs owner receives the attributed effect. The current Core method increments every call. A read-only panel must never invoke it to display morale. Exhibition end dates use `TickDay`; bind that to the canonical campaign day exactly once.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.
Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
