    itemId, category, measuredContamination, canonicalBasePrice, factionId);

**Source contract.** Accept a fact only after the owning command commits. Carry its stable ID, subject, campaign day and authored row ID through the host boundary. Distinguish a query from a mutation: `Evaluate` may mutate counters in some current Core systems, so call sites must be inspected instead of assuming the method name is pure. A panel asks for a read model; a player command asks the existing host session to validate and commit. Treat a missing subject or catalog row as a refusal before changing any destination owner.

**Destination contract.** The destination owner alone changes canonical trade settlement and faction standing owners. The host carries a typed fact or uses the owner’s established delegate; it does not copy the destination value into another mutable store. The implementation review must record method name, input ID and before/after destination state. If the destination lacks a safe command, record an authority decision rather than writing its fields directly. A projected outcome is useful only if it can be traced back to the original committed fact.

**Save and retry contract.** Capture existing radiation, trade, and standing owners; bridge counters require a custody decision before persistence after mutation and before reporting a durable result. Where two owners persist separately, the handoff must name save order and recovery for a crash between writes. A repeated fact ID after restore must be a no-op or resume one pending effect, depending on the current owner’s marker semantics. No process-local boolean can stand in for persisted applied identity. The old-save baseline should be documented with one fixture and a stable outcome; corruption should fail without partially mutating an unrelated section.

**Host lifecycle contract.** Reconstruct Core state first, then attach the producer subscription once, then expose a player surface. Reset detaches handlers and clears only transient references. Dirty tracking must follow actual state change; calling a query must not mark a section dirty unless the inspected Core method genuinely updates counters. The shared `Main` and save registry remain integrator-owned paths. The review note should include setup, save, reset and direct/indirect caller locations.

**Focused implementation specimen.** Arrange a valid source ID and a real catalog row; invoke the command or event through the current host; assert destination state and readout; capture and restore into a new session; replay the same ID; assert there is still one effect. In a second fixture, substitute the invalid reference described in the relevant casebook and assert a specific refusal with no resource, standing, stage, or wallet change. This is the minimum evidence for one vertical slice, not a request to generate a separate test for every card.

**Content handoff.** Author a short observation, a command label, a refusal, and a consequence line only in fields actually consumed by the current UI or event renderer. Use existing localization and accessibility conventions. A passage must not announce an unlock, treatment, route, or economic result before its owner confirms the state. The narrative writer receives stable IDs and the exact before/after facts, so a line of prose can be reviewed against an implementation trace.

### Projection versus transaction

The economy bridge currently looks like a quote calculator but also mutates counters. That matters: a trade panel can re-render an offer several times, and simply calling EvaluateTrade in RefreshView would inflate evaluation totals or blocked counts. The first implementation slice should decide whether evaluation counters are operational metrics worth saving or whether the bridge needs a read-only preview and a separate committed evaluation. Only the merchant/trade owner can issue a binding offer, consume stock or currency and decide whether a restriction blocks a transfer. Radiation contributes a measured constraint, not a competing market. The exact order with reputation, barter, faction standing, scarcity and difficulty must be documented at the market price boundary.

The social bridge is even more sensitive. Exposure is a medical fact; prejudice is an encountered social behavior, not a property of the survivor. `EvaluateSocialStance` can roll a chance with a supplied RNG. Run it only for a real, identified encounter and fork the canonical campaign stream by encounter ID. Persist enough of the encounter outcome with the existing event/standing owner so replay does not reroll or duplicate a standing penalty. If the encounter never occurs, no discrimination incident should be recorded. Copy should say who expressed or enforced a policy and what they knew, and avoid treating radiation as moral fault.

Both bridge classes have small save DTOs for counters, but neither needs a fresh mutable authority over item contamination or survivor dose. Use their state only after its purpose and section custody are approved. A stateless bridge variant may avoid any new section; the existing destination saves can carry the actual outcome.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 13A. Integration framework and implementation contracts

### Command boundary

A player action enters through its current Main/host route with canonical actor ID, target ID, campaign day, source event ID and catalog reference. Validate the actor and referenced content before calling the named Core owner. Return an existing ActionResult shape where one is available; otherwise propose a typed accepted/blocked result in the current host rather than passing a raw boolean to a button. The result names the committed source ID and a stable blocker key. This framework is a proposal for the implementing integrator, not a claim that the methods below already exist.

```csharp
// Proposed command context. Check current ActionResult conventions first.
public sealed class IntegrationCommandContext
{
    public string ActorId { get; init; } = string.Empty;
    public string TargetId { get; init; } = string.Empty;
    public string SourceEventId { get; init; } = string.Empty;
    public int CampaignDay { get; init; }
}
```

### Save and lifecycle order

No bridge save section is approved by this plan; source dose and destination trade/social authorities carry committed outcomes. Bridge counters need a separate custody decision if retained. Validate the catalog, create or select the one owning Core instance, restore that section, then bind event adapters and UI. Capture after an accepted command and before dirty flags are cleared. When two existing sections change in one journey, document capture order and the recovery behavior for a save between them. Restore must not replay a player reward, resource transfer, relationship delta or notification. An old save missing the section gets the documented empty or seeded baseline, not fabricated historical actions. A future schema uses the current codec rejection rule and a corrupt envelope must not masquerade as a valid empty state.

### Deterministic day and event order

Use `_simDay` or the campaign day coordinator argument, never a literal UI day or wall-clock clock. A day tick runs once per accepted campaign day and sorts unstable source collections by stable ID before effects. A read-only projection is pure; reopening a panel cannot fire a Core command. For each subscription, name where it is bound, when it is unbound, and whether restore can emit it. If the source event is retried, an owner-persisted key or already-committed state prevents the second effect; a process-local flag is insufficient.

### Player surface and accessibility

Show current state, legal action, cost and consequence, and precise blocker in the same view. Preserve keyboard/controller back and focus after an action or refresh. Display long authored text with wrapping and scroll, preserve empty states, and keep private/undiscovered content gated. A card never shows a morale, skill, resource, room or map outcome unless the matching authority has committed it. Bounded visible rows may paginate without truncating saved records.

### Reviewable phases and rollback

Phase 0 records current source/data/host evidence and an exact path claim. Phase 1 seals the owning Core command and one refusal. Phase 2 validates catalog IDs and references. Phase 3 wires save and day through current ownership. Phase 4 exposes one player route. Phase 5 adds authored content only after that route can consume it. Focused tests are selected under TEST_POLICY.md when implementation begins. A failed phase can be reverted without discarding other owner state; incomplete effects are reported as blocked, not quietly simulated in UI.
