## 1. Objective and bounded outcome

Route one witnessed campaign fact into RecordEvidence with source ID, medium, audience, confidence and day, then show a bounded public title. Only after that fact is real should the current merchant pricing owner consume the multiplier; add rumor and trade prose with explicit viewpoint and reach.

**Current state:** DEC-113 signed five perception dimensions and eight tags. Main loads the catalog, restores shelter_reputation, ticks daily, saves it and opens a panel. Host RecordEvidence exists, but the src sweep found no production producer outside selftest; scores may only decay from an empty baseline. Core GetTradePriceMultiplier and GetDominantPerceptionTitle exist, but no production price call was found. Evidence deduplication keys on source event, medium and audience.

**Non-goals:** No free reputation from panel text, direct faction-standing copy, repeated trade reward from one event, unknown audience presented as universal knowledge, or hardcoded price manipulation in a reputation panel.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

## 3. Current contract and collision firewall

- **Evidence or explicit premise:** Main.ShelterReputation already loads the catalog, restores and saves shelter_reputation, ticks daily and exposes ShelterReputationPanel.
- **Evidence or explicit premise:** Core has five dimensions and eight tags, RecordEvidence anti-farming, daily decay, GetTradePriceMultiplier and GetDominantPerceptionTitle.
- **Evidence or explicit premise:** The src sweep found RecordEvidence calls only in host and selftest, with no production event producer.
- **Evidence or explicit premise:** The src sweep found no production GetTradePriceMultiplier consumer for this system; current merchant prices have their own owner.
- **Evidence or explicit premise:** RecordEvidence deduplicates by source event ID, medium and audience faction, so two different media may legitimately carry a fact with distinct reach.
- **Evidence or explicit premise:** A ReputationTag is a public perception projection, not proof that every faction or visitor has learned it.

### Evidence transmission and public identity dossier

The system is integrated as state, save and UI but it needs facts from the campaign. `RecordEvidence` can assign a dimension, confidence, salience, information medium, source event ID and optional audience. The host wrapper exposes a simplified call, yet no production source call appeared in the src sweep. The first vertical slice should choose one event already recorded by a current owner, such as a completed trade, accepted refuge decision or verified defense result. Determine who witnessed it, how the report travelled and when it was recorded; only then may the reputation owner alter a score. A player-only private action should not become universal public knowledge.

The five dimensions and eight tags provide room for nuanced titles. `GetDominantPerceptionTitle` is a projection from current scores; it should not create a saved title string that diverges after daily decay or contrary evidence. Tags should display evidence provenance and uncertainty. A reputation panel can show witnessed reports by medium and audience and explain why a tag appeared or faded. If two reports disagree, preserve their source viewpoints rather than flattening them into an omniscient description. Add trader, refugee and radio wording as variants that cite the medium's limits.

`GetTradePriceMultiplier` is a calculated number with no observed production market consumer. The merchant or price owner should receive one bounded read at offer creation and show the resulting price there. Avoid multiplying the same offer repeatedly on refresh or applying both faction standing and reputation discounts without an explicit composition rule. Save/reload must preserve evidence IDs and score/tags; a day tick must decay once, and a repeated source event under the same medium/audience must not farm notoriety.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
