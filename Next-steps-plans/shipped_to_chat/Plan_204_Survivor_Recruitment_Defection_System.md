# Plan 204 — Recruitment and Defection — Known Candidates, Consent, and One Roster Handoff

> Integration plan revision: 2026-09-24. Source of truth: current repository source and data, then AGENTS.md, then [docs/newest-ashfall-master-expansion-authority-v2-0-complete-compiled-edition-volumes-1-57.md](../../docs/newest-ashfall-master-expansion-authority-v2-0-complete-compiled-edition-volumes-1-57.md). This document is a planning artifact. It does not claim paths or authorize a competing implementation package.

## 1. Objective and bounded outcome

Define one candidate source from a real world or faction fact, bind one RecruitmentSystem campaign to a host/save owner, then hand a successful candidate to the roster exactly once after consent, security and capacity checks. Present refusals and dangers without treating a person as stock.

**Current state:** RecruitmentSystem and recruitment_templates.json are signed under DEC-191: five campaign archetypes and six candidate templates, daily progression and defection offers. The inspected src tree had no production RecruitmentSystem construction or registered recruitment section. Existing VisitorIntegrationHostSession recruits an admitted visitor through the canonical roster, and prisoner recruitment has a separate current route. Those routes are not substitutes for the recruitment campaign owner and must not be duplicated.

**Non-goals:** No automatic survivor creation from a campaign counter, duplicate visitor/prisoner route, forced defection from a UI button, unverified faction poaching consequence, or separate population ledger.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

## 3. Current contract and collision firewall

- **Evidence or explicit premise:** DEC-191 signs RecruitmentSystem and recruitment_templates.json with campaigns, candidates and offers.
- **Evidence or explicit premise:** No production src RecruitmentSystem constructor, save section or panel route was found.
- **Evidence or explicit premise:** VisitorIntegration and prisoner systems already have distinct lawful recruitment routes.
- **Evidence or explicit premise:** RecruitmentSystem campaign success is not itself a roster AddSurvivor transaction.
- **Evidence or explicit premise:** Defection touches faction standing/security and must use a real faction member identity and consent rule.
- **Evidence or explicit premise:** Save custody is required because campaigns and offers advance over days.

### From rumor of a person to an actual resident

The Core recruitment authority can discover candidates, start campaigns and make defection offers. It persists its own campaign and offer state in a DTO, but the production host does not currently construct it. The first slice should begin with a world fact that identifies one candidate and provenance: a known settlement contact, an expedition encounter, a refugee at the airlock or a faction member with an actual source identity. `DiscoverCandidate` must not materialize arbitrary people from a panel refresh. A campaign can then track outreach over days; its status is not population.

Permanent membership belongs to the survivor roster. A successful campaign or accepted offer must pass consent, shelter capacity, airlock/security and existing visitor/prisoner custody where applicable, then call the roster owner once. If roster addition fails, the recruitment record must remain pending or blocked, not silently mark the person recruited. If the candidate is already a visitor or prisoner, hand off to that owner's route rather than creating a duplicate resident ID. Faction defection may have retaliation or standing effects, but those require a real faction owner acceptance; the recruitment system does not own diplomatic relations.

The language should describe offers, conditions and uncertainty without commodifying people. A candidate can ask about work, safety or someone already inside. A defector may refuse, reconsider or request discretion. No line should state that a candidate accepted until the Core outcome and roster handoff both commit. The UI should show known candidate, source, campaign stage, cost, capacity, consent state and the legal next action.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
