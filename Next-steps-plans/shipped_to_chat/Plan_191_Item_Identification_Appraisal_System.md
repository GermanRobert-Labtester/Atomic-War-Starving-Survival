### Retirement is an architectural conclusion, not missing work

The older plan proposed a fresh system in which ordinary scavenged items arrive unidentified, receive unique instance IDs, and require an appraisal skill to reveal properties. The current C3 disposition rejected that as an unjustified inventory-instance authority. The visible player need—understanding an item and its trade value—is already served by the inspection model and ShelterBarterSystem's appraisal behavior. This document may be made easier to read and richer in type-level copy, but its implementation steps cannot be revived by increasing word count.

The safe content surface is the existing item inspection and trade flow. A description can mention visible condition, maker marks or practical uncertainty when the current item data supports it. A merchant appraisal line may say a price is provisional if the market owner actually quotes it as such. It cannot conceal a real item property or promise a later reveal unless the inventory owner has an instance identity and the UI consumes a saved reveal state. The dedicated Plan 190 provenance chain can tell a known item's history; it does not automatically make the item mechanically unidentified.

If designers later want per-instance discovery, they must first sign an inventory-instance owner, capture/restore contract, migration from existing stacks, reveal policy, current UI route and concrete consumer. That is a new proposal, not Phase 1 of this retired plan. Until then, all acceptance cards below either verify current inspection/appraisal, improve prose under existing schemas, or record why a former greenfield task remains retired.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
