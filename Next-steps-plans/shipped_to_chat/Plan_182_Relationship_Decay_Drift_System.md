> Integration plan revision: 2026-09-24. ## 1. Objective and bounded outcome

Trace one real relationship pair through canonical bond registration, daily neglect, mitigation, drift and reconnection, with one visible effect and save parity. Keep the relationship owner authoritative for affinity while drift owns timing and events.

**Current state:** DEC-119 and DEC-175 signed six bond profiles and Core drift logic. Main constructs a host, loads catalog, ticks daily, saves relationship_decay and opens a panel. Current src search found no binding for BondingMitigationProvider or BondDriftBridge and no production calls to RegisterOrUpdatePair/RecordInteraction outside the host; pair state may remain an isolated mirror unless sourced from the canonical relationship owner.

**Non-goals:** No second pair registry deciding social bonds, no passive decay of unregistered ghost pairs, no panel-created interactions, no unbounded history, and no invented daily duty mitigation.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

## 3. Current contract and collision firewall

- **Evidence or explicit premise:** RelationshipDecaySystem exposes RegisterOrUpdatePair, GetPair, RecordInteraction, TickDay, LoadCatalog, GetProfile and CaptureState/RestoreState.
- **Evidence or explicit premise:** Its state stores pair affinity/trust as well as LastInteractionDay and DaysWithoutInteraction; the current relationship authority may also store affinity/trust, so a one-way authoritative bridge is required.
- **Evidence or explicit premise:** BondingMitigationProvider and BondDriftBridge delegates exist in Core but no src binding was found in this sweep.
- **Evidence or explicit premise:** Main.RelationshipDecay loads six profiles, registers the relationship_decay section and calls TickRelationshipDecay from the shelter day path.
- **Evidence or explicit premise:** Host RecordInteraction can synthesize an Acquaintance pair if none exists. Only a real accepted social interaction should feed it.
- **Evidence or explicit premise:** TickDay increments DaysWithoutInteraction each call without comparing a saved last-ticked day, so replay or duplicate day ownership must be audited.

### Bond authority and observed drift dossier

A domain test can show correct decay while the campaign never registers a pair. That is the primary integration risk. Current `Main.RelationshipDecay` constructs and advances its own system; no production source call to `RegisterOrUpdatePair` or `RecordInteraction` appeared outside its host wrapper in this sweep. The plan must first identify the canonical pair authority (SurvivorRelationsSystem or coordinator), choose one-way event feeding, and decide whether the drift system's affinity/trust fields are a projection or an effect request. Do not let two mutable pair records independently choose the displayed bond level. If the canonical owner lacks an attributed change method, seek a signed seam before applying drift.

The six authored profiles are live-loaded. Their decay rate, grace period, reconnection multiplier and shared-duty mitigation need an actual host provider. A shared room or shift cannot be guessed from the pair DTO. The provider should read current quarters/duty owners and return a bounded factor, while the Core drift method remains deterministic. The `BondDriftBridge` should emit one typed fact per threshold crossing; it must not copy affinity into a second relationship store. Death/departure and legacy saves need explicit pair retention or pruning rules.

`TickDay` increments counters whenever called, so duplicate host/day calls would accelerate drift. The day owner should prove one call per campaign day and restore should resume from the saved day without catch-up unless the campaign calendar explicitly requests it. The panel currently lists pairs and drift history; extend it with reason and reconnection state only after an accepted canonical interaction route exists. Preserve the semantics of rivalry, family and mentor bonds rather than treating every low affinity as friendship failure.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.
Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
