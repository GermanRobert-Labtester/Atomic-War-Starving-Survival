## 1. Objective and bounded outcome

Choose one player-founded destination that is not an authored Plan 58 outpost, route one establishment command through real expedition discovery, stock and roster checks, and present a saved colony state. Then bind one supply delivery and one building project through existing authorities; keep colony and authored outpost identities distinct.

**Current state:** ColonySystem and colony_blueprints.json are signed under DEC-155. Main.OrphanSealWave1 loads, restores, saves and daily-ticks ColonyHostSession. The src sweep found no player command invoking EstablishColony, ConstructBuilding, EstablishSupplyLine, AssignSurvivorToColony or TransferSupplies outside the Core/host wrapper path. Plan 58 has a separate active OutpostSettlementSystem and outposts.json for authored outposts, with live resource/roster integration. The old claim that no permanent presence exists is stale.

**Non-goals:** No second inventory at a colony, magic garrison duplication, new authored-outpost owner, fictional road or travel event, free building on panel click, or implicit colony founding from an expedition summary.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

## 3. Current contract and collision firewall

- **Evidence or explicit premise:** DEC-155 signs ColonySystem and five colony blueprints plus six building definitions.
- **Evidence or explicit premise:** Main.OrphanSealWave1 constructs, restores, captures and ticks colony daily through the registered colony section.
- **Evidence or explicit premise:** The inspected src tree did not show a production colony establishment or construction player command. Core EstablishColony defaults initialSupplies to 50f, and ConstructBuilding substitutes an unknown definition with a fallback; the production adapter must reject unvalidated IDs and commit real stock before calling either.
- **Evidence or explicit premise:** OutpostSettlementSystem and outposts.json already run as a distinct Plan 58 authority with garrison/ration integration.
- **Evidence or explicit premise:** ColonySystem stores internal supply and garrison references; real inventory/roster handoffs need one transaction rule.
- **Evidence or explicit premise:** A founded colony can use destination/route facts only after the current expedition/map owners confirm them.

### A founded site must be a reachable campaign object

The Core model can establish colonies, construct buildings, assign garrisons and move supplies. Its host existence proves save and day-tick reachability, but it does not prove a player can found a site. The first package must define a specific event: an expedition reaches a discoverable destination, the player chooses to establish a colony, an inventory cost and survivor assignment are accepted by their owners, and ColonySystem records the founded site with a stable identity. The destination and travel route must be known to the map/expedition owners; a text label in the colony catalog is not a geographic route.

The live Plan 58 OutpostSettlementSystem governs authored outposts and a second holdfast context. It is not a prototype to copy into ColonySystem. A colony is player-founded state under the `colony` save section; an authored outpost is a separate entity under its own section. If a future interaction connects them, use a cross-owner fact with explicit identity mapping, not shared mutable garrison or food lists. Likewise, a supply line in ColonySystem must be reconciled with real inventory stock and travel; calling TransferSupplies alone must not mint materials at the shelter or move the same ration twice.

Blueprint prose should distinguish survey, foundation, occupancy, maintenance and loss. A watchtower is not defensive until construction commits and a defense owner consumes its rating. A field clinic is not treatment until medical capacity is connected. The initial panel can show site, type, built structures, assigned people, daily supply draw and route status. It should tell the player precisely which effects are active and which remain descriptive.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

Write down exact DTO version, constructor baseline, capture point, restore point, and dirty flag. The restore sequence is: catalog validated; source state restored; destination state restored; adapters bound; pending effects reconciled once; UI bound; day processing resumes. A new campaign starts with an explicit empty/default state. A legacy save without the field takes that same baseline without inventing past events. Unknown future schema versions must fail or degrade according to the existing save contract, with a visible diagnostic. Corrupt single records must not silently reset an entire unrelated section.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.

## 9. Player commands and UI

Inspect the current route to `src/UI/ExpeditionPanel.cs` and its bind/open/close methods. Expose only commands backed by an existing Core method or a specifically planned method in the named owner. The panel should show source state, currently legal action, expected cost, blocker, committed outcome, and uncertainty where the game cannot know more. Refresh on authoritative state change and after restore; unbind subscriptions on close/disposal. Preserve keyboard/controller back and readable contrast.
