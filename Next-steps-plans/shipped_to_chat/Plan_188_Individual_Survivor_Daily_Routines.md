# Plan 188 — Individual Survivor Routines — Measured Days, One Shelter Clock, and Honest Satisfaction

> Integration plan revision: 2026-09-24. Source of truth: current repository source and data, then AGENTS.md, then [docs/newest-ashfall-master-expansion-authority-v2-0-complete-compiled-edition-volumes-1-57.md](../../docs/newest-ashfall-master-expansion-authority-v2-0-complete-compiled-edition-volumes-1-57.md). ## 1. Objective and bounded outcome

Replace one estimated daily input with a measured existing owner fact, make one routine assignment and satisfaction readout truthful, and connect conflict detection only after real room/work assignments are available. Preserve the shelter-wide clock and avoid treating routine templates as actual completed work.

**Current state:** Contrary to the old greenfield premise, SurvivorRoutineSystem, routine_templates.json, host, save section and SurvivorDetailPanel routine provider exist. Main.TickSurvivorRoutines currently derives hoursWorked=8 and socialHours=2 constants, guesses sleep and meals from current fatigue/hunger thresholds, and both BuildRoomAssignments and BuildWorkspaceAssignments return empty dictionaries with TODOs. Earlier DEBT-188 hour consumer is retired and must not be reopened: ShelterScheduleSystem.TickHour already receives canonical campaign hour.

**Non-goals:** No second global timetable, invented meal/sleep/work history, automatic duty assignment from routine label, duplicate morale reward, or per-hour simulation ledger merely to fill UI.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

### A routine is a plan; a lived day is evidence

The current individual-routine Core type has templates, chronotypes, preferences, activity-by-hour queries, daily satisfaction and conflicts. The host already persists it. The weak seam is evidence: Main calls EvaluateDailySatisfaction every day with fixed eight hours of work and two hours of social time, while inferring sleep and meals from momentary fatigue and hunger. That can award or penalize satisfaction for actions never performed. Before expanding routine schedules, identify which current owners emit accepted duty completion, meal consumption, rest and social interaction facts. If one category has no measurable fact, omit it or label it estimated; do not manufacture a daily event ledger simply to make all slots look filled.

The existing shelter-wide timetable owns day/curfew/night phase and lighting demand. The DEBT-188 schedule-hour consumer is complete. A personal routine should explain intended blocks within that global phase, but it cannot overrule a curfew or emergency protocol. Similarly DutyRoster assigns actual labor. A routine work block is a preference or forecast until a duty is accepted. The panel must distinguish intended schedule from recorded activity and show when a conflict comes from a real room/workspace assignment. Empty assignment dictionaries should yield “not assessed,” not “no conflicts.”

Day-beat prose can add texture to ordinary life: a survivor is late because a shared washroom queue formed, or shifts a meal after a repaired pump. Each candidate below requires the corresponding actual room, duty or meal fact. Avoid narrating a full day from one need gauge. The first implementation phase should wire one input, prove save/replay, then widen measurement only through existing owner events.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

A new campaign starts with an explicit empty/default state. A legacy save without the field takes that same baseline without inventing past events. Unknown future schema versions must fail or degrade according to the existing save contract, with a visible diagnostic. Corrupt single records must not silently reset an entire unrelated section.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
