## 8. Event and failure semantics for this process

A process fact is an action name, route key, catalog row, plan ID, version or evidence path. Give it a stable ID and precise origin. The receiving tool or UI resolves it through the existing authority and reports acceptance, refusal or unavailable state. Repeating a check is read-only; reopening a panel does not create game state. For Plan 53, only the foreman or named integrator changes queue and census status. For Plan 48, a dry run never becomes a published release merely because an artifact was built. For Plan 45, content presence is not consumer reachability.

## 9. Contributor or player-facing presentation

Show the current object, accepted action, refusal and next legal step. Input and navigation surfaces preserve keyboard/controller back, focus and disposal. Release and governance reports cite revision, source file, tool version and exact command. An unknown ID must not be replaced by a plausible example. A generated table must not be edited to make a status look complete.

## 10. Conditional dependency-ordered phases

### Phase 0 — Reconcile signed state

Read the live owner, relevant closeout, census and current output. Record DELIVERED, RESIDUAL, BLOCKED or STALE for each historical task. Stop if the item is sealed and no new gap is proved.

### Phase 1 — Name one failing contract

Use a real route, action, row, version or plan ID. Capture the precise current failure and the smallest owner responsible. Claim only that owner's paths, leaving shared governance and composition roots to the integrator.

### Phase 2 — Correct the owner or authored input

Change one bounded source or declaration. Run its owning generator for derived output. Keep compatibility and manual-authoring boundaries explicit. Do not widen a regression fix into a redesign.

### Phase 3 — Verify the result and recovery

Check accepted, refused, repeated and older-input cases with the smallest relevant target. For UI, inspect focus and close/back; for CI, use --check; for release, record candidate provenance and save support.

### Phase 4 — Foreman handoff

Report exact files, commands, observed output and remaining limitation. The foreman or named integrator updates shared status only after all package acceptance is met.

## 13A. Process integration framework

### Input boundary

The entry is one current plan ID, route key, action name, catalog row or version. Parse it once with the existing owner. Do not make a new registry simply to hold the same identifier. Each refusal carries an input path or control name and a code the contributor can act on.

### Authority and projection

Authoritative settings, metadata, release configuration or UI route declarations remain in their named files. Generated registers, maps, changelog regions and reports are projections. A change to a projection must be made in its source and regenerated. The framework must show which output file is generated and which fields are hand-authored before an implementer edits anything.

### Repeatability

Invoke the check twice from unchanged input and compare output. For navigation, open and close repeatedly with one live bind. For release tooling, distinguish a local rehearsal from tag creation or publication. For content intake, require a current loader and consumer rather than a fake success row.

### Compatibility

Name one preceding accepted input format and one unsupported future input. Specify how the current owner migrates, rejects or degrades. No process row creates a campaign save section. The existing settings and release save-support contracts remain separately testable.

### Handoff

The package record contains the failing input, current authority, exact claim, command, observed result and limitation. A sealed status remains sealed unless a new evidence-backed issue is signed. The foreman controls shared queue and claims; generated artifacts come from their generators.
