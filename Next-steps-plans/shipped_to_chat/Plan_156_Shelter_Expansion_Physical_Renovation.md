## 1. Objective and bounded outcome

Make one blueprint project executable through a canonical resource transaction and labor command, then reconcile completed room state with the actual shelter layout owner and show project/stability truth in the shelter UI. Keep renovation and upgrades as separate bounded slices.

**Current state:** DEC-152 signed six blueprints/four upgrades. ORPHAN-SEAL-W1 constructs, loads, restores and saves ShelterExpansionSystem under shelter_expansion; ShelterExpansionHostSession exposes ProgressProject but TickDay is intentionally a no-op. No production player calls to StartRoomConstruction/StartUpgrade/StartRenovation/StartDepthExcavation or physical room/resource settlement were found in this sweep.

**Non-goals:** No free rooms from a progress button, no parallel bed/power/air room function, no spending resource_costs in the panel, no automatic labor on day tick, and no completion claim before canonical shelter room registration.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

## 3. Current contract and collision firewall

### Physical-room and resource boundary dossier

The expansion Core is live-hosted but not yet a complete build route. It can start a project with declared ResourceCosts and labor requirements, but those costs are just fields until Inventory actually debits them. `ProgressProject` accepts a caller-supplied labor amount and can complete a room, producing an ExpansionRoomDto in its own grid. The existing shelter layout, bed capacity, power, air and room navigation are owned elsewhere. The first implementation slice must inspect their public room registration and capacity APIs, decide one canonical room identity, and ensure a project completion results in a usable room exactly once. If no safe registration seam exists, stop at a truthful project preview rather than presenting a new playable room.

The cost boundary should be explicit: choose whether costs are reserved at start or paid at completion, and persist the transaction state so save/reload cannot duplicate a room or charge twice. Labor must come from an accepted worker/duty action, with a stable project/day key; the empty TickDay remains correct until that action exists. `StartDepthExcavation` uses a fixed project ID `shaft_lv{nextDepth}` and can be retried, so the host must guard duplicates and the Core invariant should be hardened before exposing it. `StartRoomConstruction` derives IDs from day and `_projects.Count`; collision and restore ordering require scrutiny.

The six blueprint and four upgrade rows are authored design inputs. RoomTypeId and resource_costs must resolve against current room and item catalogs. Upgrade effect prose should distinguish current Core stability repair from unimplemented thermal, HEPA or acoustic effects in other owners. The shelter panel should show legal position, depth, actual stock/labor cost, project progress, stability risk and precise blocked reason; it must not promise a working hydroponic bay until that owner binds the completed room.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.
Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
