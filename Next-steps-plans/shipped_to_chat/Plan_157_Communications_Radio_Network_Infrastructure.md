## 1. Objective and bounded outcome

Make one antenna and signal journey player reachable: validate installed hardware through the existing resource/room owners, intercept a signal sourced from a real faction event, decode it with a canonical skill, save it, and present the lawful readout. Add frequency lore and more messages only after the producer and player route exist.

**Current state:** DEC-153 signed four antenna tiers, five networks and three intercept templates with Core save/restore. ORPHAN-SEAL-W1 loads/restores communications and calls DegradeAntennas(0.2) daily. CommunicationsHostSession exposes intercept, transmit, decode and degradation, but this source sweep found no production calls to intercept/transmit/decode or a dedicated communications panel. Core InterceptFactionSignal currently builds a generic [SIG_INTERCEPT] line from faction and frequency; authored intercept templates need a real consumer before lore is claimed reachable.

**Non-goals:** No second RadioManager, fake faction intelligence from a generic string, arbitrary free antenna installation, unbounded day wear without repair path, duplicate broadcast content authority, or internal-message behavior inside the long-range network system.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

### Signal provenance, antenna cost and radio-family dossier

CommunicationsSystem is already constructed and saved, and antennas wear each day. The operational gap is a complete command source. A player cannot infer an intercept from five authored network rows. The current Core InterceptFactionSignal accepts an arbitrary factionId and creates a generic raw line if range and sensitivity suffice; there is no evidence in this sweep of a real faction transmission event feeding it. Phase 0 should inventory the faction event or radio traffic producer, define a stable signal ID, source day, frequency, encryption and expected reception range, then route it into CommunicationsSystem. If the API cannot accept authored content or signal identity, extend this Core owner through a signed change; do not put generated lore in the panel. An intercept template is eligible only if its conditions correspond to an actual producer.

Installing an antenna currently belongs to CommunicationsSystem state, but build materials and physical placement remain with Inventory and shelter construction. The first player installation route needs a verified blueprint, stock transaction, valid room/site and upkeep/repair mechanism. Existing daily DegradeAntennas(0.2) should be observed against a multi-day saved campaign; it must not quietly destroy infrastructure before a repair player route exists. Repairs may consume items through Inventory, while the communications owner updates condition only after acceptance. Four hardware tiers should create visible range/sensitivity distinctions without implying unsupported world-map travel reach.

The radio family is crowded. NVIS owns its shortwave path, RadioProgramProductionSystem owns program creation and audience, InternalCommunicationSystem owns shelter notices, and CommunicationsSystem owns antennas/intercepts/outgoing reach. A produced program may supply content to a transmission command, but a transmission record is not a second program. A decoded intercept may emit a fact to faction intelligence or journal only once; a raw undecoded signal must not reveal hidden details. Present a panel with installed antenna, condition, coverage, known frequencies, intercepted messages, decode requirements and exact blockers. Content text should remain fictional and uncertain where intercepted data is incomplete.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
