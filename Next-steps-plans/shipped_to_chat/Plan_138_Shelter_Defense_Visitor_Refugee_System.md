## 1. Objective and bounded outcome

Trace one outsider arrival through airlock screening, one accepted admit/refuse decision, security clearance, a visitor stay, ration use and either departure or roster recruitment; separately trace one raid fact through existing DefenseSystem to a visible outcome. Add visitor/refugee scenarios only when their arrival trigger and consequence owner are real.

**Current state:** The original 2026-09-01 premise is stale: DefenseSystem, AirlockSecuritySystem, ShelterSecuritySystem and VisitorIntegrationSystem now exist with distinct save ownership. DEC-118 explicitly shares ShelterSecuritySystem between Plans 138 and 209. Main.VisitorIntegration already listens for a committed Airlock Admit decision, de-duplicates by source visitor ID in its host, starts a temporary stay, consumes canonical rations, and recruits through the survivor roster owner. Main also ticks/saves security and visitor integration and exposes their panels. This plan must extend that journey and actual raid handling, not create the two new systems requested by the legacy text.

**Non-goals:** No new ShelterDefenseSystem or VisitorSystem, duplicate refugee roster, automatic raid from a panel, extra rations ledger, clearance copied into a visitor DTO, fabricated faction standing, or unconditional conversion of a guest into a resident.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

- **Evidence or explicit premise:** The current visitor panel and security panel are separate surfaces; a combined journey may link them but must not move their state into a new aggregate.

### Four-owner journey and superseded-premise dossier

The original plan is a historical proposal written before the current runtime owners existed. It lists `ShelterDefenseSystem.cs` and `VisitorSystem.cs` as new files and says the shelter cannot be attacked or admit outsiders. Current source contradicts that premise: DefenseSystem resolves pre-combat raids, AirlockSecuritySystem owns hatch incidents and decisions, ShelterSecuritySystem owns internal zones, and VisitorIntegrationSystem owns admitted stays, housing, tasks, monitoring, ration demand and recruitment. The revised plan must treat these four as a sequence of owners, with exact facts and IDs at each handoff. It should not unify them into a fifth mutable manager or new save section.

The admission handoff is already concrete. Main subscribes to `OnIncidentResolved`, checks `VisitorDecision.Admit`, and calls `HandleAirlockAdmission` with `sourceVisitorId` and the source day. The visitor host de-duplicates repeat source IDs; the daily visitor route uses canonical Inventory for food/water and a roster callback for recruitment. The residual is to verify arrival generation and screening provenance, then connect internal zone access and housing to the shared Plan 138/209 security owner. A visitor's temporary housing assignment cannot imply the room exists, is safe, or is open in lockdown. Denied entry or refused admission needs a truthful departure/incident outcome; a visitor should not silently remain active with no place to stay.

The defense journey is separate. A real raid producer supplies faction, approach day, target and stable raid ID. DefenseSystem evaluates current traps and garrison state and resolves its pre-combat stage; any tactical combat, damage, stolen stock or faction response is applied by the appropriate current owner. Security lockdown can be a response to a verified alarm, but it does not resolve the raid itself. Visitor archetypes such as sick refugee, informant or hidden spy need a specific disease, intelligence or counterintelligence destination before prose promises an effect. The plan should first add one scenario to the existing `visitor_templates.json` and actual event path, then assess further content demand.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 7. State, save and migration

Inspect `src/Host/ShelterSecuritySaveStore.cs` and the registry for the named concern; absence of a section is a decision gate, not permission to invent one. Write down exact DTO version, constructor baseline, capture point, restore point, and dirty flag. For a stateless bridge, persist only the source and destination authorities; do not create a bridge section. If a new mutable field is genuinely required, version the existing owner DTO and prove migration from the preceding schema. Never equate a panel cache with campaign state.

The restore sequence is: catalog validated; source state restored; destination state restored; adapters bound; pending effects reconciled once; UI bound; day processing resumes. A new campaign starts with an explicit empty/default state. A legacy save without the field takes that same baseline without inventing past events. Unknown future schema versions must fail or degrade according to the existing save contract, with a visible diagnostic. Corrupt single records must not silently reset an entire unrelated section.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.

## 9. Player commands and UI
