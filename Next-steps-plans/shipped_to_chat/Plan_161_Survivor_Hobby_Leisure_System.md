## 1. Objective and bounded outcome

Select one real leisure command route and explicitly decide how the existing RecreationSystem session and HobbySystem proficiency cooperate. Show mastery and facility blockers from the same accepted action, persist the result, and apply morale once through Needs.

**Current state:** DEC-156 signed ten hobby rows and Core mastery/session model. ORPHAN-SEAL-W1 constructs HobbySystem, loads catalog, restores/saves hobby section and exposes HobbyHostSession.ConductSession; its TickDay is deliberately a no-op. A separate RecreationSystem and HandleDowntimeAction already run leisure sessions. No player route to HobbyHostSession.ConductSession or binding of OnSessionCompletedSeam to Needs was found in the sweep.

**Non-goals:** No second scheduled leisure system, free mastery from panel opens, default sessions for unknown hobby IDs, duplicate morale from RecreationSystem and HobbySystem, or claimed item cost without Inventory transaction.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

### Leisure owner collision dossier

The HobbySystem and the existing RecreationSystem appear to describe overlapping activities at different levels. HobbySystem owns individual proficiency, session count, mastery tier and shared-affinity calculation; RecreationSystem owns downtime session scheduling, social minimum/maximum and stress relief. The first task is a concrete owner map for every player action: either a completed RecreationSystem session feeds one HobbySystem progression record, or one explicit HobbyHostSession action is legal outside the scheduled downtime system. Avoid two buttons that both advance the same hobby on the same day. The existing HobbyHostSession.TickDay deliberately does nothing and should stay so unless a signed design adds passive activity.

`ConductSession` currently accepts any hobby ID and supplies a default definition when no authored row matches. The production command must check the ten-row catalog, living actor, schedule, facility, co-participant IDs and once-per-day policy before invoking it. The method can use ISeededRng; fork from the campaign stream with a stable action ID, never UI time. It returns MoraleGained, but the authoritative Needs owner must apply the delta once, while recreation may already apply relief. Explicit attribution distinguishes the two effects.

The residual UI is a read model: current interests, session count, proficiency, mastery, next tier, facility required and current blocker. The existing SurvivorDetailPanel is a candidate display surface; a command route may belong to the established downtime panel instead. Only the selected action owner can enable the button. Additional flavor rows or group activities should be authored after the basic session is reachable and persistence is proven.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.
Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
