## 1. Objective and bounded outcome

Replace synthetic room claims with a validated current room/occupancy query, use canonical action day for housing and tasks, and make admission-to-stay-to-recruitment outcomes observable with save/reload and ration shortfall behavior.

**Current state:** VisitorIntegrationSystem, visitor_templates.json, host, save section, airlock admission handoff, ration debit, roster recruitment and VisitorIntegrationPanel are live. The Main airlock callback deduplicates a committed Admit decision by source visitor ID. The host currently assigns synthetic visitor_berth_<id> rooms; the panel also submits fixed room IDs and passes ArrivalDay to housing commands. Existing code does not prove those IDs correspond to built/free housing or that arrival day is the action day.

**Non-goals:** No admission bypass, duplicate visitor identity, free private room from a button, ration cache, implicit dismissal on food shortfall, or permanent resident before roster AddSurvivor succeeds.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

## 3. Current contract and collision firewall

- **Evidence or explicit premise:** VisitorIntegrationHostSession and Main already bind Airlock Admit to temporary stay with source ID dedup.
- **Evidence or explicit premise:** visitor_integration is registered and captured through VisitorIntegrationSaveStore.
- **Evidence or explicit premise:** Main.VisitorIntegration draws canned_food and clean_water from canonical inventory and recruits via survivor roster.
- **Evidence or explicit premise:** Host uses synthetic visitor_berth_<id> housing IDs and panel offers fixed room IDs.
- **Evidence or explicit premise:** Panel passes visitor.ArrivalDay to housing commands, which may misdate a later reassignment.
- **Evidence or explicit premise:** Room existence, capacity, privacy and occupancy need an exact current owner before a housing button promises space.

### Admission, sheltering and becoming a resident are distinct transactions

The current host makes the first two transitions reachable: AirlockSecurity commits Admit, then VisitorIntegrationHostSession opens one temporary stay. The roster is not changed at admission. Rations are debited from shared inventory only when the full daily amount is available; a shortfall consumes nothing and does not itself eject the visitor. Integration tasks and monitoring remain with the VisitorIntegrationSystem. Recruitment asks the roster to add the visitor and closes the stay only after that succeeds. This is a good ownership spine and should be retained.

The weak seam is housing truth. A string such as `visitor_berth_` plus ID can be useful as an internal placeholder, but it is not proof of a built, powered, heated, free room. The panel's fixed strings have the same problem. Before offering “private room,” query the room/topology and occupancy owner for an actual capacity token. The housing command should use the current campaign day, not the visitor's ArrivalDay, so history and deadlines remain accurate. A failed room request should leave the existing stay and allocation intact and show why it failed.

Visitor arcs can include intake chores, contribution, unease, teaching and departure, but prose must be driven by actual task and relationship outcomes. A security finding cannot be erased by a warm narrative line; AirlockSecurity retains the incident. A host view should show admission source, current room, available space, ration status, tasks, days remaining, monitoring posture and the legal recruitment or departure action. All of these must survive restore without reopening the airlock event.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
