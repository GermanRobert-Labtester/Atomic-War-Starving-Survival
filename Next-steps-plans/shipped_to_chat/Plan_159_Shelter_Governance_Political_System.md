## 1. Objective and bounded outcome

Replace unstable automatic bloc selection with a stable ordered campaign rule, bind one real policy proposal to EvaluatePolicyConsent and one accepted grievance/dispute consequence, and present provenance and options through existing UI before adding broad political content.

**Current state:** ShelterGovernanceEngine, bloc/policy data, host, save section, day tick, survivor-detail bloc provider and dispute/consent APIs exist. Main.TickShelterGovernance autoassigns a bloc using Math.Abs(s.Id.GetHashCode()) modulo sorted keys. String.GetHashCode is not a stable cross-process deterministic seed; this path needs a deterministic identity decision before replay can be trusted. Main passes policySystem:null to the host, so any proposal claiming policy integration must first verify that bridge. No dedicated governance panel was observed in the inspected src/UI list.

**Non-goals:** No second leadership election, duplicate policy store, unseeded or GetHashCode-based bloc choice, faction-standing rewrite from a bloc label, fabricated vote, or automatic grievance from panel refresh.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

## 3. Current contract and collision firewall

- **Evidence or explicit premise:** Main.ShelterGovernance creates host, restores shelter_governance and ticks daily.
- **Evidence or explicit premise:** Core owns ideological blocs, policy consent, grievances, disputes and stability projection.
- **Evidence or explicit premise:** Main autoassigns blocs with string.GetHashCode, which is unsuitable for deterministic replay.
- **Evidence or explicit premise:** Main SetupShelterGovernance currently passes policySystem:null to host Create.
- **Evidence or explicit premise:** SurvivorDetailPanel has a PoliticalBlocProvider, but no dedicated governance panel was found.
- **Evidence or explicit premise:** Leadership and PolicySystem are separate authorities; their effects must be accepted by those owners.

### Stable political identity before richer politics

The current engine and host can represent blocs, consent and disputes, but the entry path has a deterministic flaw: Main chooses a bloc with `string.GetHashCode()` modulo sorted definitions. Hash values are process-dependent under modern .NET behavior and can change across runs. A save may preserve a choice after first assignment, yet a fresh replay or a partly restored roster can diverge before capture. The first integration phase must establish a stable rule: use a persisted authored affiliation, a stable deterministic hash with specified bytes/endianness, or a campaign RNG fork keyed by survivor ID. The implementation decision should be explicit and tested across fresh and restored processes. Existing assignments must be preserved during migration.

The host is created with `policySystem: null`, so a governance panel must not promise that consent constrains every current policy action. Pick one actual policy proposal and identify the PolicySystem method that commits it. Evaluate consent before enactment, present the prediction, and record grievance only after the policy owner reports a committed decision. If consent is advisory, say so; if it can block enactment, that must be an agreed contract with PolicySystem, not a silent panel rule. Leadership stays with its own owner and cannot be replaced by a bloc score.

Disputes need parties, grievance source, day and resolution. Text can capture institutional fatigue, scarcity and competing priorities without declaring one bloc intrinsically right. A meeting note should show what was requested and which rule applied. Stability is a projection from saved facts, not a resource to be edited from narrative choice copy.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
