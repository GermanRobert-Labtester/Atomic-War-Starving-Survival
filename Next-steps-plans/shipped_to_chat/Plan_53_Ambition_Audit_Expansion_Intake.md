## 13A. Process integration framework

### Input boundary

The entry is one current plan ID, route key, action name, catalog row or version. Parse it once with the existing owner. Do not make a new registry simply to hold the same identifier. Each refusal carries an input path or control name and a code the contributor can act on.

### Authority and projection

Authoritative settings, metadata, release configuration or UI route declarations remain in their named files. Generated registers, maps, changelog regions and reports are projections. A change to a projection must be made in its source and regenerated. The framework must show which output file is generated and which fields are hand-authored before an implementer edits anything.

### Repeatability

Invoke the check twice from unchanged input and compare output. For navigation, open and close repeatedly with one live bind. For release tooling, distinguish a local rehearsal from tag creation or publication. For content intake, require a current loader and consumer rather than a fake success row.

### Compatibility

Name one preceding accepted input format and one unsupported future input. Specify how the current owner migrates, rejects or degrades. No process row creates a campaign save section. The existing settings and release save-support contracts remain separately testable.

### Handoff

The package record contains the failing input, current authority, exact claim, command, observed result and limitation. A sealed status remains sealed unless a new evidence-backed issue is signed. The foreman controls shared queue and claims; generated artifacts come from their generators.
