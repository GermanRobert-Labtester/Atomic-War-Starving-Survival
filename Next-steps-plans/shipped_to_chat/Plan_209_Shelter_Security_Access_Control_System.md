## 1. Objective and bounded outcome

Reconcile the authored eight-zone catalog, fresh-game six-zone seed and physical room IDs, then route one real attempted movement through RequestAccess and the current movement owner. Bind one alarm response and truthful access panel without creating a second Plan 209 security simulation.

**Current state:** DEC-118 explicitly combines Plan 138 and Plan 209 under ShelterSecuritySystem, with eight catalog zones and alarm/lockdown/denial seams. Main loads the catalog before constructing the host, restores shelter_security, calls a daily method that only marks dirty, and exposes ShelterSecurityPanel. Core LoadCatalog configures all eight missing zones; the host six-zone seed is a fallback only if the catalog left state empty. Core RequestAccess records a breach for denied access to a locked zone, while no production caller outside selftest was found in this source sweep.

**Non-goals:** No second zone registry, catalog-only room treated as built, lock button that cannot affect movement, automatic breach from a read-only panel query, defense alert from an unverified attempt, or clearance granted from a display role string.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

### Shared authority, physical route and alarm dossier

The critical premise is ownership: Plan 209 is an expansion of Plan 138's ShelterSecuritySystem. A new AccessControlSystem, clearance save, door ledger or security panel state would split authority. Core LoadCatalog currently configures eight runtime zones from eight authored definitions before host construction, so the host's six-zone fallback should remain inactive when the catalog loads. The integrator must verify fallback behavior when the catalog is absent or invalid, how saved zones merge with new definitions, and whether each RoomId resolves to an actual built room. A named future room must not be treated as physically accessible merely because a JSON row exists.

RequestAccess is a command with side effects: denied restricted attempts can create a breach and alert, while permitted access does not itself move a survivor. The movement/room entry owner must call it once per actual attempted entry, then commit or reject movement based on IsGranted. Panel previews should use a side-effect-free authorization query rather than RequestAccess. In lockdown, AllAccess is the documented Core bypass; any emergency override policy must be explicit and validated against fire/medical evacuation paths. Do not let a UI clearance grant with defaults day=1, grantedBy="leader" impersonate governance authority.

AlarmRelayBridge, LockdownStateBridge and SecurityDenialLogger are existing Core seams. Bind them to the current defense/log owner only after checking whether that owner already raises an alert for the same unauthorized entry. A breach ID is the stable attribution key. Repeated RequestAccess clicks must not multiply breaches for one movement command; a genuinely separate attempt may be recorded. ResolveBreach changes the current security record but should not reset an external defense alert without the defense owner's acceptance. The panel should display zone location, clearance requirement, physical availability, lock state, active breaches and legal command roles.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
