# Plan 154 — Survivor Education and Knowledge Transfer — Real Sessions, Proficiency, and Graduation Criteria

> Integration plan revision: 2026-09-24. Source of truth: current repository source and data, then AGENTS.md, then [docs/newest-ashfall-master-expansion-authority-v2-0-complete-compiled-edition-volumes-1-57.md](../../docs/newest-ashfall-master-expansion-authority-v2-0-complete-compiled-edition-volumes-1-57.md). ## 1. Objective and bounded outcome

Create one real scheduled study session sourced from roster, age, teacher, current duty and facility facts, then commit proficiency and one skill unlock through current owners. Seal graduation eligibility and actual day semantics before adding ceremony or certificate prose. Present a truthful learner record in a claimed education surface.

**Current state:** DEC-151 signed three stages and twelve subjects. ORPHAN-SEAL-W1 loads/restores survivor_education and captures it. SurvivorEducationHostSession exposes registration, teacher/subject assignment, session and graduation commands; its TickDay is intentionally a no-op, and the src sweep found no production calls to ConductDailySession or assignment. Core ConductDailySession can call EvaluateGraduation(studentId, -1) for age 18+, while EvaluateGraduation itself only checks existence and prior graduation and then sets GraduationDay, so a direct call can graduate an untrained learner.

**Non-goals:** No second school attendance ledger, free sessions on each panel open, permanent skill from a subject name alone, teacher bonus without verified relationship, graduation at day -1, or duplicate knowledge from repeated completion.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

### Session route, skill custody and graduation dossier

This is a live Core and save authority without a production study-session route in the inspected Main path. The first slice should not add more subject rows. It should register one current learner, assign a real eligible teacher and an authored subject, confirm duty/time and schoolroom conditions, run `ConductDailySession` once with a stable campaign RNG fork, and show the returned proficiency. The learner's age comes from the roster/lifecycle owner and must update through `UpdateAge` when that owner advances. Teacher competency and parent-child status must be verified facts; the host's default values are not proof of a teacher or family relationship.

The current Core method has a graduation hazard. At age 18, `ConductDailySession` calls `EvaluateGraduation(studentId, -1)`, and `EvaluateGraduation` immediately marks any existing nongraduated record as graduated, with the caller's day. A direct host command can likewise graduate a learner before any subject is completed. Phase 1 must define graduation criteria in the existing education owner, including stage, required subjects and actual campaign day, then test refusal and a genuine completion. Do not present ceremony text or issue a certificate while a novice can graduate by invocation.

Education stores `UnlockedSkillIds` in its learner record and raises a session result, but an external survivor skill owner may also store usable skills. The plan must decide whether education's list is a source fact or an applied skill entitlement; if the latter, route one attributed grant to that existing owner and persist a stable award key to avoid duplicate grants after reload. The shelter knowledge pool also needs an explicit consumer before UI copy claims research progress. Apprenticeship and child-development systems may share actors and facilities; they must not credit the same instruction as two independent daily sessions.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
