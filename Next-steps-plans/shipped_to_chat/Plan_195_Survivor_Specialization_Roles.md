# Plan 195 — Survivor Specialization Roles — Canonical Duties, Skill Gates, and Earned Role Practice

> Integration plan revision: 2026-09-24. ## 1. Objective and bounded outcome

Establish one role assignment through canonical survivor and skill facts, then earn role XP from one accepted duty result. Persist the specialization in the chosen survivor owner and show a truthful role/bonus readout. Add role flavor only after each bonus has a real consumer and auto action is sourced from a real duty completion.

**Current state:** SurvivorRoleSystem and eight authored survivor_roles rows exist in Core/data, but the src sweep found no production construction or role host. Core AssignRole can skip required skills when the caller supplies null and can bypass all gates with force=true. TriggerAutoAction increments XP and count based on a matching action string; it does not perform the real work action. A role is a specialization, while DutyRosterSystem remains the shift owner.

**Non-goals:** No second duty schedule, free XP from a role button, force-assignment from UI, synthetic auto work, skill gate bypass by null dictionary, or bonus applied both in DutyRoster and role system.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

### Specialization versus duty and skill-gate dossier

The current role catalog is a domain capability, not yet a campaign feature. DutyRoster already decides who works where and when; the role owner should express a persistent specialization and earned proficiency. The first host command must validate a living roster survivor, an authored role, a canonical skill snapshot, the role cap and any mutually exclusive role rule. Passing null skills would skip Core requirements, and `force=true` would bypass all gates. Those arguments should be unavailable from player UI and reserved, if at all, for a documented migration path. A role assignment should not silently move a duty slot or imply an unverified facility.

An accepted duty result can carry survivor ID, role-relevant action kind, source ID and day to `AddRoleXp` or `TriggerAutoAction`; the role owner cannot award XP simply because the player pressed a label. `TriggerAutoAction` currently records an action and grants 20 XP without performing work, so using it as a work executor would create free resources or care. Decide whether it is an accounting callback after successful duty or replace that naming in a bounded Core change. A bonus from `GetRoleBonus` is only a number until a named current consumer accepts it; do not stack it twice with an existing skill or duty modifier.

The absence of a host and registered save section is an authority gate. The implementing package should inspect the survivor social/roster save lineage and obtain an exact custody decision before adding state. A new section may be warranted, but it must be registered once through the current save owner and restored before UI. The first role UI can show eligible roles, current assignment, relevant duty, earned XP, next threshold and actual bonus consumer. Additional eight-role flavor text should be selected from real work outcomes, not generic praise for unperformed labor.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
