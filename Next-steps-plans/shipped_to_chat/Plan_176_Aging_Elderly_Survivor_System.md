## 1. Objective and bounded outcome

Audit the origin and meaning of each survivor birth/age fact, make unknown age visible as unknown or explicitly estimated, then deepen stage, retirement and mentorship presentation only where current owner effects exist. Preserve current day and old-save progression.

**Current state:** AgingSystem, SurvivorAgingProgressionEngine, life_stages.json, AgingHostSession, Main day/save wiring and SurvivorDetailPanel age-profile provider are live. Main.TickAging registers each roster survivor with DefaultRecruitmentAgeYears, so an unknown personal age can become the same default age for all. The separate CampaignAgeDays clock is derived from joinedDay and currentDay and already sealed; it must not be reintroduced as stored state.

**Non-goals:** No fabricated exact birthdate, separate age counter, automatic retirement without legal command, duplicate child-development stages, or work output from a mentorship label.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

### Distinguish a known age from a convenient baseline

The aging engine and host are real, but the input quality determines whether its output is trustworthy. Main registers each active roster entry using the same `DefaultRecruitmentAgeYears` unless AgingState already holds a record. That is a legitimate compatibility baseline only if the UI labels it as an estimate and gameplay does not treat it as a verified personal history. If a canonical survivor profile carries age, use that source. If it does not, specify a stable age-at-join policy and keep “estimated” visible. Do not infer a birthday from elapsed campaign days or invent a year/month calendar when gameplay uses days.

Chronological age and campaign tenure differ. The derived CampaignAgeDays clock tells how long someone has lived in the shelter; it should not be persisted as a second mutable field. Life stage definitions govern age bands, milestone thresholds and retirement eligibility. Retirement is a choice/transition with duty consequences, not an automatic synonym for reaching a threshold. Mentorship needs a real education or apprenticeship session with a living elder mentor and accepted learner progress. `HasLivingElderMentor` alone cannot grant XP.

Writing should preserve personhood: an elder can be skilled, tired, resistant to retirement, or willing to teach. Status text should describe current capability and stated preference, not a deterministic stereotype. A milestone letter can cite a recorded shared project; it cannot claim a decades-long backstory if the save knows only the last ten shelter days.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
