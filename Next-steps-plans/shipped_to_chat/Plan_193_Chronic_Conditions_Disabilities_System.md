# Plan 193 — Chronic Conditions and Accommodations — Clinical Attribution, Function, and Respectful Care

> Integration plan revision: 2026-09-24. Source of truth: current repository source and data, then AGENTS.md, then [docs/newest-ashfall-master-expansion-authority-v2-0-complete-compiled-edition-volumes-1-57.md](../../docs/newest-ashfall-master-expansion-authority-v2-0-complete-compiled-edition-volumes-1-57.md). ## 1. Objective and bounded outcome

Audit one long-term condition and its true diagnostic owner, then bind an accommodation request through a current room/duty owner and a lawful private panel readout. Decide state/save custody for genuinely new condition records before building a host. Use respectful copy focused on capability and care, not a moralized disability score.

**Current state:** ChronicConditionSystem and chronic_conditions.json exist in Core/data with AddCondition, AssignAccommodation, capability modifier and save DTO. A src sweep found no production construction or call for that named system. AfflictionsPanel already presents chronic radiation illness, lung damage and dependency through existing medical/radiation owners. Therefore a new chronic-condition host cannot copy those records into a parallel diagnosis ledger without an explicit mapping and custody decision. The Plan 198 medical record log is already sealed within the medical pipeline.

**Non-goals:** No duplicate chronic radiation flag, diagnosis from a tooltip, automatic work penalty without duty owner, public medical disclosure, disability-as-failure language, or new health-history ledger.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

- **Evidence or explicit premise:** Medical privacy limits which UI or public event may reveal a condition.

### Diagnosis, function and accommodation are different facts

The Core proposal can hold a named long-term condition and an accommodation, but current medical systems already own several chronic facts. Radiation's chronic illness flag, lung damage and dependency appear in AfflictionsPanel. Duplicating them in a ChronicConditionSystem state would create two diagnoses that can drift after treatment or save/restore. The first phase should select one condition that is genuinely absent from current owners, or define a read-only projection of an existing diagnosis. If a new durable record is warranted, sign the save section and migration map before the host constructs it. A one-time diagnostic source event with stable ID is required; opening the medical panel cannot create a condition.

An accommodation is a practical change to work, space or equipment. `AssignAccommodation` can record an intent, but an actual lighter duty must be accepted by DutyRoster; a ramp, modified bunk or mobility path must be accepted by room/infrastructure owners; a maintenance item must come from inventory. If the destination cannot honor the accommodation, the record should say requested or unavailable rather than fulfilled. A capability modifier should be consumed at one calculation point and balanced against skills, tools and accommodation; avoid a global blanket penalty.

Writing should name the concrete task and support. A clinician can record fatigue after stairs, a worker can request a bench nearer the door, or a clerk can note a modified shift. The text should not reduce a person to a condition or imply all disabilities are acquired, tragic or permanent. Private medical details belong in clinical surfaces; public duty views need only the accommodation relevant to the action.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 5. Data and identity contract

Canonical IDs come from the existing catalogs and runtime facts. Case handling, trimming and comparison must match the owning system. Proposed new IDs need a schema and reference validator before a producer can emit them. Read the current JSON fields before extending a row; do not use the old plan’s desired row count as an acceptance measure. Reject duplicates or conflicting definitions with per-row diagnostics. Treat display names and prose as presentation, never identity. Preserve ordinal ordering for stable output and save checksum inputs.

A change to catalog shape requires an old-catalog compatibility rule, one example valid row, one invalid row, and a reader inventory. New prose must state a real observed consequence; it cannot promise trade, safety, quest or reward behavior until a consumer reads the corresponding Core fact. Avoid real-world names or copied narrative.

A new campaign starts with an explicit empty/default state. A legacy save without the field takes that same baseline without inventing past events. ## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.

## 9. Player commands and UI

The panel should show source state, currently legal action, expected cost, blocker, committed outcome, and uncertainty where the game cannot know more. Refresh on authoritative state change and after restore; unbind subscriptions on close/disposal. Preserve keyboard/controller back and readable contrast.
