## 1. Objective and bounded outcome

Bind one real survivor trait or event to one personal-quest trigger, one accepted gameplay action to one requirement, and current campaign day to choice. Preserve ownership of actual rewards/consequences, and write arc text that fits a named survivor context without assuming unrecorded backstory.

**Current state:** PersonalQuestSystem, personal_quests.json, host, registered save, daily tick and PersonalQuestPanel are live. The inspected src tree had TryTriggerQuest and ProgressRequirement calls in host wrapper/selftest but no production source trigger. The panel calls ChooseOption with hardcoded currentDay 1, which can misdate outcomes. The headless demo is not proof of production reachability. Current authored arcs may be displayable only through selftest initiation.

**Non-goals:** No quest initiation from panel render, fabricated survivor memory, duplicate generic questline master, free progress from repeated events, hardcoded day 1, or direct resource/morale mutation by prose.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

- **Evidence or explicit premise:** PersonalQuestHeadlessDemo and selftest show Core capability, not production event reachability.
- **Evidence or explicit premise:** Consequences and rewards must route through actual survivor, inventory, needs or faction owners.

### Personal quest as a sequence of witnessed actions

The quest owner already has state, catalog, host and panel. The gap is the source of an arc. A trait ID or lived event should be verified against the roster and trait owner, then admitted into PersonalQuestSystem once with a stable source fact. The current host's TryTriggerQuest wrapper and selftest are not enough to make an arc appear during a campaign. Choose a single current producer, such as a completed caregiving action or a known trait-driven situation, and trace it to trigger. Then choose one requirement whose progress can be read from a committed action owner. A failed or canceled action must not progress the quest, and retrying an action ID must not grant progress twice.

The panel is reachable but currently passes day 1 when a player chooses an option. That needs the canonical campaign day so deadlines, history and consequences remain coherent. The panel must show current state, choices, blockers and result without making choices during refresh. Rewards belong to inventory, relationships, morale, traits or faction systems as appropriate, and may require an explicit authorized command. If the personal quest engine records completion but the reward owner refuses, show the pending or failed handoff rather than claiming the reward arrived.

Arc text should be written from plausible records and voices. A brief note can ask for a repair, a recovered tool or one conversation. It should not assert a survivor's childhood, family or former profession solely from a generic trait. Candidates below are keyed to triggers and source facts; implementation must confirm the current JSON schema and localization before promoting any line.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 5. Data and identity contract

Canonical IDs come from the existing catalogs and runtime facts. Case handling, trimming and comparison must match the owning system. Proposed new IDs need a schema and reference validator before a producer can emit them. Read the current JSON fields before extending a row; do not use the old plan’s desired row count as an acceptance measure. Reject duplicates or conflicting definitions with per-row diagnostics. Treat display names and prose as presentation, never identity. Preserve ordinal ordering for stable output and save checksum inputs.

A change to catalog shape requires an old-catalog compatibility rule, one example valid row, one invalid row, and a reader inventory. New prose must state a real observed consequence; it cannot promise trade, safety, quest or reward behavior until a consumer reads the corresponding Core fact. Avoid real-world names or copied narrative.

## 7. State, save and migration

Inspect `src/Host/PersonalQuestSaveStore.cs` and the registry for the named concern; absence of a section is a decision gate, not permission to invent one. Write down exact DTO version, constructor baseline, capture point, restore point, and dirty flag. For a stateless bridge, persist only the source and destination authorities; do not create a bridge section. If a new mutable field is genuinely required, version the existing owner DTO and prove migration from the preceding schema. Never equate a panel cache with campaign state.

The restore sequence is: catalog validated; source state restored; destination state restored; adapters bound; pending effects reconciled once; UI bound; day processing resumes. A new campaign starts with an explicit empty/default state. A legacy save without the field takes that same baseline without inventing past events. Unknown future schema versions must fail or degrade according to the existing save contract, with a visible diagnostic. Corrupt single records must not silently reset an entire unrelated section.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.

## 9. Player commands and UI

Inspect the current route to `src/UI/PersonalQuestPanel.cs` and its bind/open/close methods. Expose only commands backed by an existing Core method or a specifically planned method in the named owner. The panel should show source state, currently legal action, expected cost, blocker, committed outcome, and uncertainty where the game cannot know more. Refresh on authoritative state change and after restore; unbind subscriptions on close/disposal. Preserve keyboard/controller back and readable contrast.

### Player surface and accessibility

Show current state, legal action, cost and consequence, and precise blocker in the same view. Preserve keyboard/controller back and focus after an action or refresh.
