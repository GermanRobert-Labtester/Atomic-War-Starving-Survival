## 1. Objective and bounded outcome

Expand authored region and POI presentation through WastelandMapSystem knowledge, strengthen survey provenance and map UX, and make any map purchase or skill proposal prove a canonical owner first. Preserve one fog ledger.

**Current state:** DEC-158 signed CartographySystem and eight map_regions rows, but live Main and MapPanel use only static ProjectCanonicalMap over WastelandMapSystem.Knowledge. Main.RecordCartographySurvey calls WastelandMap.DiscoverSurvey and shared SkillProgressionSystem scavenging XP. No src construction of a stateful CartographySystem was found. This is a deliberate one-map ownership boundary, not simply a missing host.

**Non-goals:** No second map save, no copying CartographyState.Regions into world knowledge, no fake POI discovery from prose, no independent cartography XP ledger, and no free purchase without a trade transaction.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

- **Evidence or explicit premise:** The unused CartographySystem.PurchaseOrAcquireMap and internal CartographySkill would duplicate trade and skill authority if blindly hosted.

### One-map authority dossier

This plan has a more subtle premise than the September draft. The Core CartographySystem defines regions, surveys, a skill ledger and map purchases, but the live campaign intentionally projects cartographic quality from the canonical WastelandMapSystem rather than instantiating the stateful object. `ProjectCanonicalMap` maps Unknown/Rumored/Surveyed/Visited to 0/30/65/100 quality and sorts by node ID. `Main.RecordCartographySurvey` updates WastelandMap knowledge and awards existing scavenging XP. A plan that constructs CartographySystem and saves its Regions would create a second fog-of-war truth. Keep the stateful API unhosted unless a signed decision identifies a nonoverlapping concern and migration.

The eight `map_regions.json` records are useful as authored geography if mapped to actual WastelandMap node IDs. Phase 0 must inventory every region_id, point_of_interest and current node/location ID, then classify matches, aliases and missing links. A region description may appear at rumor quality, but hazard certainty, POI list and route safety must respect the canonical fog/provenance level. Content cannot reveal undiscovered coordinates merely because JSON contains them. Map purchases must use existing economy/inventory transactions and WastelandMap rumor/survey commands; no standalone PurchaseOrAcquireMap call may bypass them.

The residual UX can improve MapPanel: a selected node shows discovery state, survey quality, source/day, relevant authored lore and legal survey action, with focus and controller back. Save/reload follows world map and skill owners only. A separate CartographyState migration is a decision-gated proposal, not a baseline requirement.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 7. State, save and migration

Inspect `src/Host/WastelandMapSaveStore.cs` and the registry for the named concern; absence of a section is a decision gate, not permission to invent one. Write down exact DTO version, constructor baseline, capture point, restore point, and dirty flag. If a new mutable field is genuinely required, version the existing owner DTO and prove migration from the preceding schema. Never equate a panel cache with campaign state.
The restore sequence is: catalog validated; source state restored; destination state restored; adapters bound; pending effects reconciled once; UI bound; day processing resumes. A new campaign starts with an explicit empty/default state. A legacy save without the field takes that same baseline without inventing past events. Unknown future schema versions must fail or degrade according to the existing save contract, with a visible diagnostic. Corrupt single records must not silently reset an entire unrelated section.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.
Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.

## 9. Player commands and UI

Refresh on authoritative state change and after restore; unbind subscriptions on close/disposal. Preserve keyboard/controller back and readable contrast.
