## 1. Objective and bounded outcome

Choose and prove one real covert-operation producer consistent with the existing EspionageSystem boundary, then route a resolved operation to one canonical consumer: an attributable intel report, faction response or security incident. Show the report status and suspicion with exact source and day. Add archetypes and prose only after a producer can launch and a player can observe the outcome.

**Current state:** DEC-150 signed five operation definitions and suspicion bands. ORPHAN-SEAL-W1 loads the catalog, restores faction_covert_ops through a checksummed payload, advances the coordinator daily with a campaign RNG fork, and captures its state. The host exposes LaunchOperation, AdvanceDay and GetSuspicion; the current src sweep found no production launch call or player covert-ops panel route. EspionageSystem already owns player-deployed agent missions. A prior orphan seal repaired in-flight operation restore, so re-audit that path rather than reimplementing it.

**Non-goals:** No second player espionage command store, fabricated agents, direct standing mutation from an intel summary, instantaneous sabotage without a named target owner, hidden faction knowledge shown before decode, or duplicate operation on save/retry.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

### Covert owner and operational custody dossier

The old plan framed espionage as greenfield, but the repository has two distinct authorities. `EspionageSystem` handles player-deployed missions; `FactionCovertOpsCoordinator` handles the rival-faction operation and suspicion model retained under `faction_covert_ops`. The host comments state this boundary explicitly. The first implementation package must select a source: a faction AI/event launching a rival operation or a player action delegated to the existing player espionage owner. Do not expose `FactionCovertOpsHostSession.LaunchOperation` as a second player mission button without a foreman authority ruling. The Core method currently accepts arbitrary agent ID and caller supplied stealth factor, so a production gate needs a verified actor, target faction, availability and skill source.

Daily advancement is real, but a day tick does nothing interesting without an active operation. A successful operation creates an `IntelligenceReport` with raw text, accuracy and `IsDecoded=false`; decoded knowledge is a distinct state. A sabotage or assassination label cannot be taken as proof that a target room, NPC, equipment item or faction resource changed. The report needs source operation ID, recipient visibility and a typed destination fact. If the faction-standing or defense owner cannot accept that fact, leave it pending and present an intel report rather than silently mutating another system. Threat and suspicion changes should be observable at each band, with a reason and countermeasure route that owns any cost.

The orphan seal already fixed in-flight restore. The residual acceptance should include a save midway through an operation, resolution after reload, exact one report, one suspicion transition and no duplicate compromise. The five authored archetypes can be expanded after each has a legal producer, an actual target owner and a player-facing report. Keep intelligence prose uncertain when the report is raw or low accuracy; a displayed sentence must not reveal an unearned map node or faction plan.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
