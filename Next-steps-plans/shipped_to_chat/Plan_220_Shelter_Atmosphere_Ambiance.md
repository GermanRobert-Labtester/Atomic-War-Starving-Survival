## 1. Objective and bounded outcome

Replace unsupported environmental assumptions with named observations from existing owners, stabilize day/profile transitions, then map the committed profile to one accessible lighting, sound and descriptive UI projection. Preserve the existing Needs application and audit whether it feeds back into the next social-warmth input.

**Current state:** DEC-121 signed seven profiles and Core ambiance delegates. Main loads the profile catalog, restores both atmosphere and noise, updates atmosphere daily, applies active morale modifier through Needs and exposes a panel. The observed day route derives lighting from PowerGrid, sound from ShelterNoise, warmth from thermal and social morale; ventilation presence, cleanliness and some baselines are fixed values. Host composes Atmosphere and Noise. Current plan work is a measured source audit, feedback-loop review, sensory VFX/audio projection and content, not creation of another atmosphere authority.

**Non-goals:** No parallel room environment store, sound engine in Core, fabricated ventilation quality, double morale from profile callbacks, constant daily mood alert, or sensory effect that conceals a gameplay blocker.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

## 3. Current contract and collision firewall

- **Evidence or explicit premise:** ShelterAtmosphereHostSession composes the atmosphere read model with ShelterNoiseSystem and calculates acoustic comfort from its current noise level.
- **Evidence or explicit premise:** Main derives lighting from PowerGrid and thermal comfort from boiler fuel, but it currently uses a ventilation-presence shortcut for air purity and a fixed cleanliness value.
- **Evidence or explicit premise:** Main derives social warmth from survivor morale, then applies an atmosphere morale modifier later in the same day; the next day input may reflect yesterday’s effect, so stability must be measured.
- **Evidence or explicit premise:** Core has seven authored profiles, UpdateEnvironmentalInputs, EvaluateAtmosphere, BroadcastActiveAmbiance, CaptureState and RestoreState.
- **Evidence or explicit premise:** MoodBroadcastSeam and ProfileModifierApplier exist, but actual Godot sensory cue consumers must be found before claiming lighting/VFX/audio integration.

### Facet provenance and feedback dossier

Plan 220 is already a live day system. The existing host combines Atmosphere and ShelterNoise, Main reads PowerGrid and thermal state, and the panel can show profile and noise. The residual is precision. Main sets air purity to 80 whenever a ventilation session exists, otherwise 75, and cleanliness to 75. Those numbers describe session presence, not measured air or sanitation. Phase 0 should trace the actual ventilation and hygiene owners and map their public readings into normalized atmosphere inputs, or label an input explicitly unknown. A missing source should preserve a documented fallback without letting UI state claim verified clean air. Room-specific mood text requires a real room observation; a global composite cannot prove each corridor is warm and quiet.

The daily morale bridge is already present. Because social warmth comes from morale, an atmosphere boost can influence the next day's composite and then reapply another boost. This might be intended steady-state behavior or an accidental feedback loop. The plan should calculate bounds and transition hysteresis under seeded multi-day replay before changing the formula. The implementing integrator should separate a descriptive atmosphere read model from permanent needs effects and decide whether the modifier is an ongoing per-day delta, capped trend or one-time threshold event. Do not add a second application through ProfileModifierApplier while Main applies one already.

Presentation consumes the committed profile and mood: color/lighting palette, ambient audio cue, small diegetic description, and readable accessibility alternative. Godot should own the VFX/audio implementation and the existing audio registry should own cue identity. Core stores no texture path or Godot object. A profile transition should change cues once, and re-opening the panel should not fire mood broadcasts. The user can see each observed facet, the contribution to composite score, and whether a sensor is unavailable.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 7. State, save and migration

The restore sequence is: catalog validated; source state restored; destination state restored; adapters bound; pending effects reconciled once; UI bound; day processing resumes. A new campaign starts with an explicit empty/default state. A legacy save without the field takes that same baseline without inventing past events. Unknown future schema versions must fail or degrade according to the existing save contract, with a visible diagnostic. Corrupt single records must not silently reset an entire unrelated section.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
