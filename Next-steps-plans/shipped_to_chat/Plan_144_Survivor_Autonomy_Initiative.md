## 1. Objective and bounded outcome

Bind autonomy to real opportunity facts and one canonical consequence owner at a time, beginning with a verifiable action that survives save/reload and appears in a survivor readout. Use the existing daily owner and stable seeded ordering. Expand action content only after every new template has a trigger, recipient, refusal behavior and consumer.

**Current state:** DEC-143 signed 20 action templates and Core save/restore. ORPHAN-SEAL-W1 loads the catalog, restores survivor_autonomy, calls EvaluateDaily for roster members and writes a journal line for a returned action. The current call supplies survivor.Morale and survivor.Fatigue but no traits, target or pair affinity; Help templates requiring target cannot be selected from that path. Core exposes action and help/project/refusal seams, but this sweep found no src bindings for them. The host TickDay is a no-op; Main owns the current daily evaluation.

**Non-goals:** No automatic work assignment from a flavor line, fabricated Help target, duplicate project authority, copied relationship or morale ledger, random action from UI opening, or blanket morale for a merely narrated action.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

### Opportunity, consequence and agency dossier

Autonomy already generates a journal-visible event. That event is not proof that the survivor helped a specific person, refused an actual assigned duty, initiated a real project or changed a relationship. Current Main reads roster morale and fatigue and calls EvaluateDaily without opportunity context. The Core selector can choose categories allowed by its generic gates, but Help needs a target and the host does not supply one. Phase 0 should inventory each of the 20 templates by trigger kind, required trait, target requirement and actual destination. Choose one accepted vertical slice with a real source: for example, a known duty assignment for Refuse or a lawful relationship target for Help. The selected consumer decides whether the action can commit. Journal prose follows that result; it must not precede a rejected consequence.

The stateful Core system uses its injected ISeededRng and records a recent action and cooldown before invoking its seams. That makes event ordering and failed consumer commands important. If a destination rejects the effect after Core records an Accepted action, expose a typed reconciliation result or move eligibility validation before selection; do not silently give the player a completed action with no benefit. The day owner should sort roster IDs or prove its existing order stable across saves. An action needs a stable ID across a retry, and the destination must apply its attributed mutation once. Goal progression for Pursue belongs to the existing goal state; an unrelated project should not be created from a title string.

The first player surface can be a small survivor-detail readout of recent accepted initiative, stated intention, goal progress and exact refusal response where one is legal. Any override button must inspect the duty owner and show the consequence Core actually records. Template expansion should follow a coverage table: category, real producer, eligible actor, optional target, consumer, blocked reason, cooldown, observed line, and restore behavior. Cultural flavor can vary without introducing an unowned morale or relationship state.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
