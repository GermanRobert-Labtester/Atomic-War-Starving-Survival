## 1. Objective and bounded outcome

Bind one real acute incident owner to TriggerDisaster with stable incident ID and affected built room IDs, then route one protocol through actual staff/resource owners, apply bounded damage to a current facility owner, and expose state and warning through current UI/alert routes.

**Current state:** DisasterResponseSystem and disaster_templates.json are signed under DEC-154. Main.OrphanSealWave1 constructs, restores, saves and ticks current disasters daily with a seeded Shelter fork, and journals resolutions. The inspected Main path did not show a production TriggerDisaster source or player protocol activation command; a live tick over an empty list is not an operational disaster feature. EmergencyAlertSystem Plan 194 is a separate warning authority, not an incident detector.

**Non-goals:** No random disaster merely to populate panel, second fire/flood simulation, protocol that repairs without personnel/resources, duplicate warning per day tick, or disaster damage stored only in a narrative sentence.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

### A response system needs an incident, not just a day tick

The signed Core system can create an acute disaster, activate a protocol, tick containment and assess damage. The host currently restores it and advances active records daily. Without a producer, the active set can remain empty forever. Pick one current incident source—such as a confirmed electrical fire or sump flooding event—and define an adapter carrying source incident ID, disaster type, exact built room IDs, severity and day. TriggerDisaster should be idempotent across repeated source callbacks and save/reload. If Core cannot key on source ID, extend its own state or use a named durable mapping in the same disaster section.

Protocols represent organized response, not a magic damage-reduction switch. A fire suppression protocol needs available people, equipment and supplies committed by duty/inventory or fire owner. A pump overdrive protocol needs a real powered pump and water/flood consumer. Its Core mitigation percentage is a domain calculation; the destination facility owner must accept the resulting damage/repair effect once. The alert owner may display a warning, but a warning cannot independently trigger the hazard or consume response supplies.

The player view should show source, rooms, severity, current containment phase, response choices, resource cost, blockers and observed damage. Prose must be functional: where is the affected room, what is known, what is still uncertain, and who issued the instruction? Resolution copy should wait for both DisasterResponseSystem and underlying hazard owner to agree the event is closed.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 5. Data and identity contract

Canonical IDs come from the existing catalogs and runtime facts. Case handling, trimming and comparison must match the owning system. Proposed new IDs need a schema and reference validator before a producer can emit them. Read the current JSON fields before extending a row; do not use the old plan’s desired row count as an acceptance measure. Reject duplicates or conflicting definitions with per-row diagnostics. Treat display names and prose as presentation, never identity. Preserve ordinal ordering for stable output and save checksum inputs.

A change to catalog shape requires an old-catalog compatibility rule, one example valid row, one invalid row, and a reader inventory. New prose must state a real observed consequence; it cannot promise trade, safety, quest or reward behavior until a consumer reads the corresponding Core fact. Avoid real-world names or copied narrative.

The restore sequence is: catalog validated; source state restored; destination state restored; adapters bound; pending effects reconciled once; UI bound; day processing resumes. A new campaign starts with an explicit empty/default state. A legacy save without the field takes that same baseline without inventing past events. Unknown future schema versions must fail or degrade according to the existing save contract, with a visible diagnostic. Corrupt single records must not silently reset an entire unrelated section.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.

## 9. Player commands and UI

Inspect the current route to `src/UI/ShelterPanel.cs` and its bind/open/close methods. Expose only commands backed by an existing Core method or a specifically planned method in the named owner. The panel should show source state, currently legal action, expected cost, blocker, committed outcome, and uncertainty where the game cannot know more. Refresh on authoritative state change and after restore; unbind subscriptions on close/disposal. Preserve keyboard/controller back and readable contrast.
