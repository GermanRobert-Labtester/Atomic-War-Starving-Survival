## 1. Objective and bounded outcome

Expose the current runtime selection and legal custom scalar/lock commands on a truthful settings surface, audit every remaining scalar consumer against the one provider, and prove selection, restore and calculation parity. Keep campaign header identity and runtime settings synchronized according to the signed contract.

**Current state:** DifficultySettingsSystem, eight slider lanes, a shared DifficultyPresetCatalog, host session, difficulty_settings save section, Main commands and starting-cohort preset selection are live. Main routes EffectiveProvider into _difficultyScalars. Current src/UI/SettingsPanel does not visibly call the runtime SelectDifficultyPreset or SetDifficultyCustomScalar commands in the inspected references. Existing XP-01 scalar consumers need a per-consumer audit; the old claim that no difficulty system exists is stale.

**Non-goals:** No second preset catalog, duplicate scalar multiplication, invented ninth slider, mid-campaign mutation of locked settings, fabricated achievement labels, or gameplay effect merely from a tooltip.

**First deliverable:** one vertical slice with a real producer fact, one canonical destination owner, save/reload parity, and a truthful player readout. Later slices are separate claims and must repeat the premise check.

## 3. Current contract and collision firewall

- **Evidence or explicit premise:** Main.DifficultySettings creates a session over the existing XP-01 catalog, not a second loader.
- **Evidence or explicit premise:** DifficultySettingsHostSession exposes eight named scalar lanes and EffectiveProvider.
- **Evidence or explicit premise:** difficulty_settings has a registered save section; the campaign header also carries the identity preset.
- **Evidence or explicit premise:** StartingCohortSetupPanel binds difficulty presets and returns DifficultyPresetId at campaign start.
- **Evidence or explicit premise:** Main has SelectDifficultyPreset, SetDifficultyCustomScalar and LockDifficultySettings; the inspected SettingsPanel references did not expose them.
- **Evidence or explicit premise:** Current scalar consumers and the exact remaining unbound lanes must be established per calculation before editing.

### One selection, two persisted representations, one effective provider

The old plan proposed building a difficulty system from scratch. Current code has a signed Core settings authority, runtime host, save section, eight slider names and campaign-start selection. The header preset is campaign identity; the runtime settings section is current selection, custom values and lock. A fresh campaign, legacy save, saved custom game and locked game require explicit precedence. The existing Main setup seeds from the header when no runtime section exists, and ApplyDifficultySettingsToScalars replaces the XP-01 provider. The panel should display what is actually active, which lanes are adjustable and why a lock refuses changes. It must not promise a scalar effect until a current calculation consumer reads it.

Make a consumer inventory of radiation, raids, needs, economy, expeditions, weather, crafting and other advertised lanes. Record the exact field read, phase of calculation, rounding and composition with other modifiers. Each lane either has a validated current consumer or is described in the UI as pending and kept out of player promises. A preset tooltip should compare concrete effects, not abstract adjectives. The old proposal's nine sliders and a named sharable custom configuration exceed the current signed eight-lane contract and require a separate decision.

Locking is a campaign state transition, not an accessibility constraint. Failure must leave the effective provider and saved state untouched. Changing an unlocked preset updates provider once, affects future calculations, and should not retroactively rewrite already resolved raids, trades or injuries. Preserve a snapshot of scalar inputs for recorded outcomes when historical explanation needs it; avoid a separate mutable difficulty ledger.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 5. Data and identity contract

Canonical IDs come from the existing catalogs and runtime facts. Case handling, trimming and comparison must match the owning system. Proposed new IDs need a schema and reference validator before a producer can emit them. Read the current JSON fields before extending a row; do not use the old plan’s desired row count as an acceptance measure. Reject duplicates or conflicting definitions with per-row diagnostics. Treat display names and prose as presentation, never identity. Preserve ordinal ordering for stable output and save checksum inputs.

A change to catalog shape requires an old-catalog compatibility rule, one example valid row, one invalid row, and a reader inventory. New prose must state a real observed consequence; it cannot promise trade, safety, quest or reward behavior until a consumer reads the corresponding Core fact. Avoid real-world names or copied narrative.

## 7. State, save and migration

Inspect `src/Host/DifficultySettingsHostSession.cs` and the registry for the named concern; absence of a section is a decision gate, not permission to invent one. Write down exact DTO version, constructor baseline, capture point, restore point, and dirty flag. For a stateless bridge, persist only the source and destination authorities; do not create a bridge section. If a new mutable field is genuinely required, version the existing owner DTO and prove migration from the preceding schema. Never equate a panel cache with campaign state.

The restore sequence is: catalog validated; source state restored; destination state restored; adapters bound; pending effects reconciled once; UI bound; day processing resumes. A new campaign starts with an explicit empty/default state. A legacy save without the field takes that same baseline without inventing past events. Unknown future schema versions must fail or degrade according to the existing save contract, with a visible diagnostic. Corrupt single records must not silently reset an entire unrelated section.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.

Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
