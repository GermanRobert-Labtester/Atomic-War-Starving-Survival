## 1. Objective and bounded outcome

Complete the already live rationing overlay by loading four policy rows, routing one lawful protocol/tier command, proving the existing economy section restores rationing exactly once, and showing exact authorized allocation and crisis state.

## 3. Current contract and collision firewall

- **Evidence or explicit premise:** ResourceRationingSystem has four JSON protocol rows and supports LoadCatalog, ApplyProtocol, SetRationTier, AssignSurvivorPriority, AuthorizeAllocation, DeclareCrisis, ResolveCrisis and CaptureState/RestoreState.
- **Evidence or explicit premise:** EconomyHostSession constructs the one Rationing instance, forwards tier/crisis events, embeds CaptureState in MarketState.rationing, and has RestoreSave for both market and rationing.
- **Evidence or explicit premise:** Main.SetupEconomy currently calls _economy.Market.RestoreState(save) after EconomyHostSession.Create may have loaded the same save; this is a restore-order and duplicate path premise to reconcile, not evidence that rationing is wholly unsaved.
- **Evidence or explicit premise:** InventoryHostSession.RationingAuthorizer is bound in Main.Economy and blocks a single consumption when the decision is unauthorized or allocates below one unit. Other resource consumers need separate evidence.
- **Evidence or explicit premise:** AuthorizeAllocation returns a non-mutating decision; the actual consumer must spend stock through its current owner.
- **Evidence or explicit premise:** The existing host forwarder triggers journal voice and metrics from one tier-change event; restore must not re-fire those events.

### Existing economy overlay dossier

Plan 215 is not a blank host integration. The canonical ResourceRationingSystem is already constructed in EconomyHostSession, its snapshot is nested in MarketState.rationing, and InventoryHostSession asks it for authorization before a consumable use. The plan must preserve that arrangement. Source inspection found a likely restore discrepancy: EconomyHostSession.Create loads and restores MarketState plus Rationing; Main.SetupEconomy then reads the same save and restores Market alone. The implementing agent should trace the actual campaign-aggregate restore path and eliminate duplicate setup without losing old save support. This is a focused code change, not a reason for a new ration section.

`AuthorizeAllocation` decides an amount but does not debit inventory, water, medicine or power. It also sets Authorized true for positive demand and valid resource even when stock is zero, then returns zero AllocatedUnits with a reason. Callers must check `AllocatedUnits`, not only Authorized. The current inventory consumer already does this for one-unit use. A food or water day-consumption bridge must identify its existing consumer and compare exact units before applying effects; no blanket hook can be assumed from the catalog. Priority weights and protocol morale scales belong to the existing owner, with mood changes applied through NeedsSystem only if a signed event path exists.

No source reference to `rationing_protocols.json` in `src` was found, so the four authored rows may be unused at runtime. Load and validate them before applying a saved ActiveProtocolId. The panel should expose the current tier per resource, active crises, projected allowed units and specific refusal reason. It must distinguish policy from stock shortage.


Before code edits, inspect existing equivalent producers and consumers with `rg`, read their public methods and save snapshots, and write a one-page premise note. If another live owner already mutates the target concern, use it. If a required write API does not exist, return the proposed consumer hook to the foreman as an authority decision. Do not create a side ledger to bypass that missing API.

## 8. Event, day and failure semantics

One semantic fact should carry stable source ID, campaign day, owning entity ID, content ID if any, and enough context for the destination owner to decide. The host may route the fact but may not calculate a competing gameplay rule. Define when the fact is emitted, when a command is committed, and what is durable before the next callback. A read-only query must not create journal entries or rewards on every panel refresh.
Use the canonical day owner only for behavior that genuinely changes with time. Preserve the current day phase ordering and forked seeded RNG contract. No wall-clock seed, hash-order iteration, or System.Random belongs in deterministic Core. Replay after load must not repeat a completed effect; an effect that was not committed must remain recoverable. When a destination owner rejects a command, keep the source fact and show a reason rather than writing a partial substitute effect.
