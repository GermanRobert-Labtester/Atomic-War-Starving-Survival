# E1 Plan Integration [12] — Audio Accessibility, Mix Legibility, Critical-Cue Equivalence, Ducking, Diagnostics, and User Preferences

> **Sequence rule:** this file is `E1_planintegration[12].md`.
> The next files are `E1_planintegration[13].md`, `E1_planintegration[14].md`, and so on.
> The bracketed sequence number remains immediately before `.md`.

## 0. Mission

This plan converts Plan 169 into an implementation-grade accessibility and mix-legibility programme.

The source plan already establishes the most important architectural boundary: this work does **not** own
adaptive ambience or music-state selection. Plan 07 Task 7C owns reactive ambience/music states, crossfades,
and required music assets. E1-12 consumes resolved host-side cue/state identifiers only.

The purpose of this plan is to guarantee that a player can understand critical game information even when:

- music is loud;
- ambience is dense;
- radio is speaking;
- several alerts happen close together;
- the player has reduced hearing;
- the player has one ear available;
- the player plays muted;
- the player uses a low-dynamic-range setup;
- the player prefers reduced stimulation;
- the player is in a noisy physical environment;
- a loop or repeated signal would otherwise mask a higher-priority cue.

Audio remains a presentation layer. Simulation never waits for, reads, or branches on an audio event.

The implementation standard is:

**simulation emits canonical game meaning; host presentation chooses audio and visual equivalents; user
preferences affect presentation only.**

## 1. Scope Boundary

This plan MUST NOT create:

- `AdaptiveAudioSystem`;
- `MusicDirector`;
- `music_layers.json`;
- a Core audio save section;
- seeded audio variation;
- gameplay state derived from audio playback;
- campaign-specific bus levels;
- campaign-specific ducking state;
- audio events that simulation reads back;
- a second game event bus hidden inside accessibility mappings.

This plan MAY create or extend:

- host-side audio bus configuration;
- host-side cue metadata;
- host-side accessibility mapping;
- user audio settings;
- visual equivalents for essential cues;
- ducking/priority rules;
- reduced-stimulation preset;
- diagnostics;
- tests;
- documentation.

## 2. Core Accessibility Thesis

For every gameplay-critical cue there must be a canonical **meaning identifier** independent of sound.

```text
Simulation / host bridge emits canonical event meaning
        |
        +--> audio presentation route
        |      +--> bus
        |      +--> cue / voice / radio
        |      +--> priority
        |      +--> ducking request
        |
        +--> accessibility presentation route
               +--> localized visual equivalent
               +--> icon / notification category
               +--> persistence / coalescing policy
```

The visual equivalent is not generated by listening to audio. It is generated from the same canonical event
meaning that caused the audio presentation.

## 3. Critical Design Principles

1. **Semantic parity, not waveform parity.**<br>
   The visual equivalent should communicate the gameplay meaning, not describe the sound.

2. **Presentation-only settings.**<br>
   Volume, dynamic range, subtitles/cue indicators, reduced-stimulation choices, and audio muting belong in
   user preferences, not campaign save state.

3. **Priority beats loudness.**<br>
   Critical radio/alerts should become intelligible by reducing competing buses, not merely making everything
   louder.

4. **No hidden audio dependency.**<br>
   A muted player must still receive every gameplay-critical signal.

5. **Bounded notification load.**<br>
   Accessibility equivalents must not become an unreadable second alert feed.

6. **Stable bus semantics.**<br>
   Music, ambience, UI, alerts, radio/voice, and master output must have defined ownership and routing.

7. **Quiet is a feature.**<br>
   Reduced-stimulation and mute/pause behavior must be intentional, testable, and free from endlessly stacking
   loops.

8. **Diagnostics are safe.**<br>
   Debug audio state is read-only presentation diagnostics and cannot mutate simulation.

## 4. Initial Critical Cue Inventory

The source plan names these required categories:

- alarms;
- low-power;
- geiger escalation;
- raid start;
- medical emergency;
- expedition return;
- radio interruption.

The premise audit must expand the list only where the repository proves other gameplay-critical audio exists.

The cue inventory must classify each item as:

- Critical — missing it can materially change gameplay outcome.
- Important — useful but not required for core state comprehension.
- Flavor — no accessibility equivalent required unless design chooses one.

Only Critical cues are mandatory for visual equivalence.
