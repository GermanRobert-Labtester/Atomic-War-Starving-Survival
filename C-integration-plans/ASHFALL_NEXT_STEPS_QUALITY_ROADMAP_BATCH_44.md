## 1. Purpose and exit condition

Batch 44 converts Batch 43’s authority spine into practical settlement capacity: safe movement, emergency response, durable materials, food and soil knowledge, communication infrastructure, and bounded cultural participation. It should make resources and risk visible without adding a generic crafting ledger, a second power system, a second outbreak system, or a new “civilization score” writer.

Its exit condition is that transport, fire response, beacons, soil, food, light, shelter, and cultural records all use conserved inputs and existing host/core boundaries. Civilizational review and wellbeing are transparent read models over authoritative state, not new progression engines.

## 3. Non-goals

- No free resources, infinite production, or scene-local switches for bridges, fires, food, light, or shelter.
- No real-world military references or combat mechanics in battlefield archaeology.
- No hard-coded wellbeing/civilization victory state.
- No new bus, clock, map, inventory, medical, archive, or save envelope.
- No Unity assets, `.unity`, `.prefab`, `.asset`, `JsonUtility`, `System.Random`, or `Guid.NewGuid()` additions.

## 4. Shared resource contract for this batch

Before feature work, define or reuse a Core resource-flow DTO containing input IDs and quantities, output/byproduct IDs, labor/time, energy/fuel/water, capacity, maintenance, quality, contamination, spoilage, and interruption state. The contract must support partial work and preserve consumed-vs-reserved quantities. Every system must declare its owner for inventory, power, water, health, and location capacity.

For infrastructure, model availability as a state derived from capacity, staffing, maintenance, weather, access, and damage. For food and materials, model byproducts and waste; do not turn a recipe into an item without accounting for inputs. For reviews, retain metric provenance and missing-data reasons.

### Slice 44.1 — Transport and emergency infrastructure

- **Step 691 — Ferry/pontoon bridges:** model route endpoints, capacity, load/weight limits, construction inputs, staffing, inspection, water/weather gating, damage, maintenance, closure, and safe evacuation. A closed bridge must produce a visible reason; it must not silently teleport survivors or inventory. **Done when:** a unit test constructs a bridge at capacity, attempts one more crossing than capacity allows, and asserts the closure reason string is non-empty and the over-capacity survivor/inventory state is unchanged (not moved, not duplicated, not deleted) after the rejected attempt.
- **Step 694 — Fire brigade:** model crew availability, training, equipment, water/fuel, response time, fire severity, smoke exposure, competing incidents, fatigue, and failed/late response. Reuse existing needs/health/disease effects and location damage rules; do not create a duplicate health system. **Done when:** a unit test triggers two simultaneous fire incidents with one available crew, asserts exactly one incident is serviced (deterministically, by a defined priority rule — e.g. severity then location order — not by iteration/dictionary order, which is nondeterministic across .NET versions), and asserts the unserviced incident's damage/smoke exposure applies through the existing health/disease system rather than a bespoke stat.
- **Step 698 — Radio beacons:** model beacon placement, power draw, range, signal quality, maintenance, outage, weather/interference, identity/authentication, and uncertainty. Reuse the Batch 43 communication contract; a beacon should provide route or safety information, not person tracking. **Done when:** a unit test asserts no beacon API accepts or returns a specific survivor's live location — only route/hazard/safety information — and a second test asserts beacon range degrades under a configured weather/interference condition by a specific, asserted amount (not just "less than before").

**Tests:** bridge capacity and closure, fire-resource contention, smoke/health consequences, beacon outage/interference, deterministic response ordering, interruption, save/load/checksum, and accessibility of emergency status.

**Risk callout (missing in original plan):** competing-incident arbitration (Step 694) and closure-reason UX (Step 691) both require deterministic tie-breaking. Per AGENTS.md Invariant 4, do not use dictionary/set iteration order or `System.Random` for this — use `ISeededRng` or an explicit, documented priority rule. This was not called out as a risk in the original plan despite the batch's own "deterministic response ordering" test bullet implying awareness of the risk.

### Slice 44.2 — Soil, material, food, light, and shelter chains

- **Step 696 — Pedology:** use observation/provenance records for soil samples; model strata, pH/texture/nutrients or other defined units, contamination, confidence, remediation effort, and seasonal change. A missing sample must remain unknown. **Done when:** a unit test queries an unsampled location and asserts the result is a distinct "unknown" state (not a default/zero value that could be misread as "no contamination"), and a second test asserts a sampled location's stored values do not silently change across a season boundary without an explicit re-sample or decay rule firing.
- **Step 693 — Mycelium materials:** model substrate, moisture, growth time, contamination, labor, yield/quality, failure, and safe handling. Reuse agriculture/biology catalogs and avoid a magical unlimited material conversion. **Done when:** a unit test runs the same substrate/moisture/labor inputs through a full growth cycle twice with the same seed and asserts identical yield/quality/failure outcomes (determinism), and a third run with insufficient substrate input asserts a proportionally reduced or failed yield, not a silently-ignored input deficit.
- **Step 699 — Goat dairy:** connect animal condition, feed, water, labor, health, milking capacity, spoilage, contamination, season, and byproducts to existing food/medical authorities. Respect welfare and interruption. **Done when:** a unit test starves/dehydrates the animal's feed/water input below a defined threshold and asserts milking capacity decreases (not just animal "health" as an isolated number disconnected from output), and a spoilage test asserts milk past its shelf-life window is flagged unsafe rather than silently remaining consumable.
- **Step 702 — Vineyard:** model soil suitability, water, labor, season, disease/weather, yield, spoilage, and preservation. Do not assume wine or food outputs are guaranteed. **Done when:** a unit test runs a vineyard cycle under an adverse weather/disease condition and asserts yield can reach exactly zero (not just "reduced"), proving the "not guaranteed" language is an enforced code path, not aspirational prose.
- **Step 701 — Rush lights:** account for rush/wick/fuel inputs, work time, burn duration, smoke/fire risk, light output, and PowerGrid interaction. A low-tech light is still a finite resource. **Done when:** a unit test burns a rush light for its full stated duration and asserts it then produces zero light output and cannot be reignited without new fuel input (no infinite/reusable light source), and asserts its fire-risk flag can be queried by the fire-brigade system from Step 694 (cross-slice integration, not just isolated existence).
- **Step 703 — Felt yurts:** model fiber, water, labor, weather protection, capacity, setup/relocation, wear, and repair. Reuse shelter/location capacity rather than a parallel housing metric. **Done when:** a unit test asserts a felt yurt's capacity is read through the same `LocationLayoutSystem`/shelter-capacity API used by existing permanent shelter (not a separate `YurtCapacity` field), so capacity queries elsewhere in Core don't need yurt-specific branching.

**Tests:** conservation of water/feed/fuel/fiber, contamination and spoilage, seasonal failures, capacity, maintenance, smoke/fire consequences, deterministic production, and restored partial jobs.

**Scope-creep flag (missing in original plan):** six distinct production/consumption chains (pedology, mycelium, dairy, vineyard, rush lights, felt yurts) in one slice, each touching food, health, shelter, or power authorities, is a large blast radius for one slice under a single "Slice 44.2" heading. Per the Cross-Tool QA Rule in AGENTS.md ("any system introducing ≥2 new coupled variables must be implemented by one tool and reviewed by a different tool"), and per this project's own "one system per task" git rule, this slice should be split into at least 3 separate implementation tasks/commits (e.g. soil+mycelium, dairy+vineyard, rush lights+felt yurts) rather than landed as one unit, even though they can be planned together.

### Slice 44.3 — Records and low-risk culture

- **Step 695 — Wax tablets:** treat tablets as a durable medium connected to the communication/provenance system. Model wax/tablet quantity, legibility, corrections, privacy, and reuse; do not make it a second message store. **Done when:** a unit test writes a correction to an existing tablet entry and asserts the original text remains retrievable with a "superseded" marker (audit trail), rather than being overwritten in place.
- **Step 697 — Macramé:** use existing material/labor/recipe rules and create a provenance-backed artifact with quality, interruption, and accessibility metadata. **Done when:** a unit test interrupts a macramé job partway through and asserts the partial-completion state (percent done, consumed-vs-reserved material) is captured by `CaptureState`/restored by `RestoreState` and resumes from the same point, not from zero.
- **Step 692 — Folk instruments:** model material, construction, tuning/maintenance, participation, access, consent, and cultural record. Route morale/culture effects through existing systems rather than inventing an independent happiness score. **Done when:** a unit test asserts a folk-instrument participation event calls into the existing morale/needs API (e.g. `NeedsSystem.Modify(..., NeedKind.Morale, ...)`) rather than writing to a new standalone happiness field — verify against `NeedsSystem`'s actual `NeedKind` enum (`Hunger, Thirst, Fatigue, Warmth, Morale, Health, Hygiene`, confirmed in `Assets/Ashfall.Core/Survivors/NeedsSystem.cs`) before implementation, since "morale" already exists as a tracked need and this step must route through it, not beside it.
- **Step 689 — Ballet:** represent practice/performance, venue, labor, accessibility, consent, injury risk, and archive/provenance. It is a cultural activity, not a new progression tree. **Done when:** a unit test asserts a performer's injury-risk event applies through the existing health/medical system (not a new injury enum), and a consent-withdrawal test asserts a withdrawn performer's prior performance records are marked with restricted access rather than deleted (data integrity vs. privacy, not erasure).
- **Step 690 — Battlefield archaeology:** make this evidence-only. Record location, artifact custody, uncertainty, disturbance, privacy, and interpretation. No combat, enemy-position, real-war, or glorification mechanics. **Done when:** a unit test asserts no API in this feature accepts or returns combat-outcome data, enemy-position data, or named-real-war references, and the same `DataRuleComplianceTests.cs` gate mentioned in AGENTS.md's world_history.json resolution note (no real countries/wars/people) is extended to cover this feature's new data files.

**Risk callout (miscategorized in original plan):** the slice heading calls this "low-risk culture," but Step 690 (battlefield archaeology) is explicitly content-sensitive per this project's own tone rules ("no glorified violence," "no real countries/wars/people") and per Batch 47's own safety-review pattern for defense-adjacent infrastructure (longbow towers/hornwork). Battlefield archaeology should carry the same explicit safety-review gate that Batch 47 applies to Steps 738/743, not be bundled into a "low-risk" slice by default. Recommend moving Step 690 out of "low-risk culture" framing and requiring the same "document intended nonviolent value, no-targeting behavior, alternate design if unsatisfiable" review Batch 47 Section 7 describes, before implementation.

### Slice 44.4 — Derived reviews, last

- **Step 700 — Civilizational review:** create a read-only report over authoritative food, infrastructure, records, education, health, and culture indicators. Show methodology, source records, missing data, confidence, and trend; do not mutate metrics or choose an ending. **Done when:** a unit test calls the report generator twice in a row with no state changes in between and asserts byte-identical output both times (idempotence) and an unchanged save checksum, and a second test asserts calling the report generator never triggers a `CaptureState`/dirty-flush write on any of the systems it reads from (true read-only, verifiable by asserting no `OnPowerChanged`/`OnNeedChanged`/etc. events fire during report generation).
- **Step 704 — Wellbeing index:** use existing needs, health, safety, social, access, and care read models. Show dimensions and uncertainty, protect private records, and distinguish "not measured" from "poor." Do not add a competing morale or victory writer. **Done when:** a unit test queries wellbeing for a dimension with no underlying data and asserts the result is a distinct "not measured" value (not 0, not null treated as "poor"), and a second test asserts the index has no public method that sets or triggers a win/loss/ending state (grep-verifiable: no call from this feature's code into `EpilogueMatrixRuntime` or any ending-state writer).

These reviews should be the final integration tests for the batch. Repeated evaluation must be idempotent and must not alter the save checksum. **Ordering note (correction):** Slice 44.4 depends on data produced by Slices 44.1-44.3 (transport/fire/beacon/food/culture indicators feed the civilizational review and wellbeing index) — this dependency is implicit in the "last" heading but should be stated explicitly as a hard gate: do not begin Slice 44.4 implementation until at least one working instance of each upstream indicator category exists, or the review/index will either crash on missing inputs or need to be rewritten once real data shapes are known.
