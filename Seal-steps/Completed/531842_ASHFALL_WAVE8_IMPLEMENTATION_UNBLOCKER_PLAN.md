## 2.4 Stop conditions that override sequencing

- The required authority does not exist and the work would create a second competing owner.
- The task requires a foreman/product decision explicitly identified in this plan and no signed choice exists.
- A path is actively claimed by another agent according to the canonical ownership ledger.
- The repository HEAD has already implemented the blocker and the supplied evidence is stale. In that case, convert the task into verification + ledger correction; do not reimplement.
- A generated file is the only visible location of the required change. Locate its generator/source; never hand-edit generated truth as the primary fix.
- The observed behavior contradicts the blocker premise. Capture the contradiction and update the task's evidence before proceeding.

# 3. Global implementation contract

## 3.1 Authority rule

Every state mutation must have one canonical domain owner. Panels render read models and dispatch commands; they do not recompute economy, medical, survivor, inventory, debt, needs, or assignment rules. Host/session layers coordinate access; they do not become a second state authority. Derived projections stay derived unless persistence is required to preserve behavior across reload and that requirement is proven by an existing contract or a signed decision.

## 3.2 Parity-before-tuning rule

When replacing a direct path with a shared contract, first preserve current numeric behavior. The initial migration gate is legacy parity under a pinned seeded scenario. Any subsequent balance change must be explicit, data-authored where the repository pattern requires data authorship, and separately evidenced. Do not combine architecture migration and balance tuning in one opaque diff.

## 3.3 Determinism rule

A migration that should be behavior-preserving must not introduce RNG, wall-clock dependence, unordered iteration effects, or event-order ambiguity. Where the subsystem already has replay/fingerprint infrastructure, the task must produce same-seed/same-input equality and a mid-reload suffix comparison when save/load participates in the behavior.

## 3.4 Save rule

Before adding DTO fields, prove that state cannot be derived from already persisted canonical state. If new persistence is required, use an additive/versioned contract consistent with the repository's save patterns, add old-save/default handling, round-trip tests, mid-journey reload tests, and regenerate any save/authority matrices. Never persist a UI projection merely to make a panel easier to implement.

## 3.5 UI rule

Player surfaces must be reachable through the canonical panel registry/router/game-flow path, event-driven rather than per-frame where the surrounding surfaces use events, disposable without subscriptions leaking, keyboard operable, non-color-exclusive, bounded at the supported reference resolution, and backed by snapshot evidence when the snapshot matrix covers the surface.

## 3.6 Test rule

A red baseline is not permission to add more red. Every task records the baseline it inherits, the focused tests it owns, and the aggregate gate required at handoff. A stale assertion is changed only after the live model is proven correct. A model defect is fixed in the model, not normalized into a weaker test. Flaky/order-dependent failures are treated as defects until proven otherwise.

## 3.7 Evidence packet required for every task

Each handoff must contain: repository HEAD/commit tested; claimed paths; files changed; decisions consumed; before-state evidence; after-state evidence; focused commands and results; build result; deterministic/save evidence where applicable; generated artifacts regenerated; documentation/ledger rows updated; known deferrals; and a one-line statement of which next task is now unblocked.
