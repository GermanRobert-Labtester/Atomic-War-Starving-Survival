[VENUS-001]  Severity: CRITICAL  |  Type: broken gameplay loop  |  Status: NEW
  Location:      MapHazard_VenusTrap.cs EnterNode (line 56-69), AttemptHarvest (line
                 ~75-110); ExpeditionSystem.Tick.cs TryVenusTrapOnLootingArrival
                 (line ~217-240, uncommitted)
  Description:   The VenusTrap is fundamentally broken:
    
    (a) traps_active is NEVER decremented. AttemptHarvest checks
        `if (traps_active <= 0)` and fires OnTrapTriggered, but there is NO
        `traps_active--` anywhere in the file. Grep for `traps_active--` returns 0.
        So the 2-4 traps armed by EnterNode are never cleared.
    
    (b) EnterNode unconditionally re-arms on every call:
        `_state.traps_active = 2 + rng.Next(3);` — no guard like
        `if (_state.traps_active > 0) return;`.
    
    (c) ExpeditionSystem.TryVenusTrapOnLootingArrival calls EnterNode on EVERY
        looting arrival to a swamp node. So every visit re-arms 2-4 traps, and
        because traps are never decremented, swamp nodes are PERMANENTLY trapped
        at 2-4 active traps with no way to clear them.
    
  Player impact: swamp nodes are permanently lethal. Every expedition to a
  swamp node loses an arm (strength < 0.6) or barely escapes. There is no
  way to clear the hazard. This is a broken gameplay mechanic.
    
  Suggested Fix:
    (a) Decrement traps_active in AttemptHarvest on any successful resolution
        (both escape and amputation): `_state.traps_active = Mathf.Max(0, _state.traps_active - 1);`
    (b) Guard EnterNode to not re-arm if traps_active > 0 (unless the node id
        changed — i.e. a genuinely new visit to a *different* node).
    (c) Only call EnterNode on the FIRST visit to a node, not every looting
        arrival. Track visited/victory state per node.
  Suggested Harden: EditMode test — enter swamp node, trigger N traps, assert
  traps_active reaches 0 after N resolutions and EnterNode on a revisit does
  not re-arm.

[HMG-001]  Severity: HIGH  |  Type: non-functional promoted content  |  Status: NEW
  Location:      Weapon_HMG.cs (InventoryItemId = "weapon_hmg"),
                 HatchDefenseSystem.GetMountedHmgDefensePower (line 385-386),
                 GameBootstrap.InitLate.cs (line 870-890)
  Description:   The HMG was promoted to live (REPROMOTE-Weapon-001) and wired
  into hatch defense, but the enabling ITEM `weapon_hmg` is NOT in the item
  catalog: no entry in Assets/StreamingAssets/Data/items.json, no entry in
  Item_WorldCatalog. 
  
  The host checks `inv.CountById("weapon_hmg") > 0 || inv.CountById("hmg") > 0`
  at InitLate.cs:879-880. Since the item cannot be acquired (not in catalog),
  CountById is always 0, so GetMountedHmgDefensePower always returns 0.
  
  Result: the HMG is dead weight — the wiring exists but the player can never
  obtain or use the weapon. The +28 defense power is unreachable.
  
  Suggested Fix: Add the `weapon_hmg` item to the catalog (items.json + importer)
  so players can acquire it. Ensure it appears in WorldLootFaction tables or
  crafting recipes.
  Suggested Harden: CI gate — every item id referenced by a live system
  (IsWeaponId, InventoryItemId, CountById) must exist in the item catalog.
  Track this with a referential-integrity test that greps all ItemId constants
  and asserts each is in the catalog.

[HMG-002]  Severity: MEDIUM  |  Type: dead code path  |  Status: NEW
  Location:      Weapon_HMG.cs Fire (line 75-99)
  Description:   Weapon_HMG.Fire() is never called outside Weapon_HMG.cs. The
  hatch defense path only uses GetHatchDefensePower (a flat additive bonus via
  the InitLate delegate). So the entire jamming/shredding/ammo risk-reward
  mechanic — Fire() sets isJammed, fires OnHMGJammed, fires OnRaidShredded —
  is bypassed. The HMG provides a static +28 (or +34 with double-count) with
  no jam risk and no re-supply cost.
  Suggested Fix: Either (a) wire HatchDefenseSystem to call WeaponHMG.Fire()
  during a raid resolution (passing operators, oil state, raid level), so
  jamming/shredding actually happen; or (b) remove Fire() and document that
  the HMG is a flat passive bonus.
  Suggested Harden: EditMode test — simulate a raid with an HMG, assert the
  jam/re-shred events fire (or that the design is passive-only with a comment).

[HMG-003]  Severity: MEDIUM  |  Type: double-counting  |  Status: NEW
  Location:      HatchDefenseSystem.GetWeaponPower (line 358-390)
  Description:   GetWeaponPower iterates all inventory slots via
  GetItemDefenseContribution (which counts weapon_hmg at base 6 via
  GetWeaponBasePower), THEN adds GetMountedHmgDefensePower (up to 28). So a
  stocked + mounted HMG contributes 6 + 28 = 34. The comment at line 443
  claims "Avoid double-counting full value" but the base 6 from the slot
  iteration is still added alongside the mounted 28.
  Note: because weapon_hmg is not in the catalog (HMG-001), this double-count
  is currently unreachable. But if the item is added, the double-count becomes
  live. Fix both together.
  Suggested Fix: In GetItemDefenseContribution, skip weapon_hmg/hmg items
  (they are handled by the mounted-power path), OR have GetMountedHmgDefensePower
  return a delta-over-base (28 - 6 = 22) instead of the full 28.
  Suggested Harden: Hatch defense smoke test — assert a stocked+mounted HMG
  contributes exactly 28 (not 34).
