# EXPANSION 125 — Five Days of Warning

## Turn existing crisis warnings into a shelter preparation board that helps compare real actions without simulating a second campaign.

## Wave 24: A Feature at Its Owner

## Planning status

**Key feature:** Actionable resource runway and crisis preparation board  
**Classification:** Live-system extension  
**Anchor:** CrisisPredictor, Main.BriefingCrisis, DailyBriefingReportBuilder, and canonical stock/power owners  
**Artifact:** evidence-grounded design plan only; no production code or gameplay data changed.

## 1. Expansion thesis

Ashfall already projects food, water, fuel, radiation, sanitation, distress, demographic, and weather risks from bounded read-only inputs and adds warnings to the daily briefing. A preparation board extends that feature: preserve confidence and source limits, let players inspect the cause and compare only actions for which current owners can provide honest previews. It does not replace the predictor or duplicate the briefing.

## 2. Player value and scope

This plan centers one player-facing capability and divides it into exactly three unique subfeatures. They are distinct acceptance boundaries of the same key feature, not unrelated expansions. Working behavior is named and preserved. A missing path is called missing only where current source review supports the claim; an extension is labeled as an extension. The casebooks below are proposed checks, not existing or passing tests.

| Evidence area | Current source | What the audit establishes |

Reconfirm the source-to-owner route before implementation; do not convert comments, stale plans, or scanner mappings into proof of reachability.

## 4. Player-facing contract

The promise is **Actionable resource runway and crisis preparation board**. The feature is integrated only when its current owner, command or event source, persistence where needed, and observable player result agree. This document does not authorize a parallel mutable authority.

## 5. Decision gate

Keep the board read-only until the player chooses an existing command. Do not persist a second prediction ledger, create another model, or auto-apply advice. If a command cannot preview honestly from canonical inputs, show unavailable rather than a simulated result.

## 6. Explicit exclusions

- No predictor replacement, severity meter duplicating confidence, automated rationing, production/consumption adjustment, hidden certainty, or background action execution.
- No guarantee the event occurs on the displayed day; retain current horizon/confidence semantics.
- No repeated tick notifications; dismissal/cadence uses current briefing and panel lifecycle contracts.

## 7. Dependency-ordered implementation sequence

1. Map each crisis class to its source fields and note neutral/unavailable inputs.
2. Build a read-only board from current CrisisPredictionRecord values and refresh when campaign owners change.
3. Link/preflight only commands with existing honest previews and inputs.
4. Verify evaluation/rendering does not mutate, duplicate warning sources, or break accessibility/focus.

## 8. Shared invariants

1. One authority owns every mutable fact. Core computes; host adapts; Godot panels issue existing commands and display truthful state.
2. JSON is the authority for authored IDs, conditions, strings, and thresholds. A declaration or scanner entry is evidence to verify, not proof of player reachability.
3. Persist through the actual save-section owner. Restore rehydrates facts without replaying actions or side effects; absent legacy fields use the existing neutral/default contract.
4. Deterministic behavior uses current seeded inputs and stable ordering. Never use wall-clock time, unseeded randomness, or UI callbacks to own a gameplay choice.
5. Every refusal is neutral and visible: stale preview, invalid ID, wrong phase, absent owner, canceled dialog, and unavailable data cannot silently commit.
6. Do not build parallel caches for facts already represented by the named system. Derived display values are recomputed from the owner.
7. Voluntary actions remain voluntary unless current contract already defines automatic behavior. Forecasts retain uncertainty and source attribution.
8. Implementation requires a fresh premise audit, exact file claim, focused verification, save review, and closeout in the current project ledger.

## 9. Three unique subfeatures

The following three sections are the complete decomposition of the key feature. Each has its own promise, owner boundary, refusal contract, and verification casebook.

### Subfeature 1 — Runway Cards Name Their Evidence

**Player promise:** Player can tell the resource, projected horizon/confidence, and live stock/burn or power value supporting each warning.  
**Owner:** `CrisisPredictor records and Main.BriefingCrisis input assembly; board is read-only.`  
**State contract:** Predictions are derived. Recompute when source state changes; do not keep stale card or local runway cache.  
**Presentation boundary:** Campaign preparation board linked from current briefing, one row per current prediction; neutral defaults are visibly distinct from measurements.

#### Evidence-to-contract reading

Displayed class, day, confidence, reason, and metric match current record; unsupported source is never called observed fact. Missing owner, invalid stock, stale campaign day, or absent prediction renders unknown/empty rather than invented estimate. Treat these as paired acceptance and refusal clauses. If fresh source inspection disproves either premise, revise the plan before implementation rather than adding a workaround.

#### Commit, restore, and command path

Start from the owner named above. Validate IDs and phase against that owner, execute one domain command, and let that owner publish the resulting state. The presentation route may request, preview, confirm, cancel, and render; it cannot create a substitute state or compute a different outcome. Predictions are derived. Recompute when source state changes; do not keep stale card or local runway cache. Before commit, preview and dialog state are disposable. After commit, duplicate callbacks resolve to the same result and cannot emit another reward, relation change, unlock, phase transition, or resource mutation. Restore rehydrates existing facts and is never a new command.

#### Data, save, determinism, and accessibility

Resolve authored IDs through the current catalog and validate references with the integrity path. Capture and restore through the actual owner; do not infer a new save section. Repeat identical inputs under the existing seeded contract and keep ordering stable. The interface identifies unavailable or stale information honestly and preserves close/back, focus, refresh, and disposal behavior.

#### Player-visible acceptance statements

- Displayed class, day, confidence, reason, and metric match current record; unsupported source is never called observed fact.
- Missing owner, invalid stock, stale campaign day, or absent prediction renders unknown/empty rather than invented estimate.
- The selected command and affected target are visible before confirmation; the result is read back from its owner afterward.
- Cancel, close, back, invalid input, and stale preview leave the domain unchanged.
- Save/load preserves the result without replaying a side effect.
- Missing authoritative data displays unavailable/unknown instead of an approximation stored in a panel.

### Subfeature 2 — Preparation Choices Preview the Real Command

**Player promise:** From a warning the player inspects a relevant existing preparation action and real preflight without the board becoming a gameplay owner.  
**Owner:** `Domain command owning the action: inventory, power, sanitation, medicine, station, or campaign route.`  
**State contract:** No shadow inventory, hypothetical mutation, cloned simulator, or local what-if counter. Compare actions only with a pure owner preview.  
**Presentation boundary:** Board link opens existing owner panel/preflight with return path and focus restoration.

#### Evidence-to-contract reading

Preview reads same state as canonical action preflight; accept executes that command once; cancel is neutral. Unpreviewable action is an unavailable row or destination link, not fabricated success/cost/certainty. Treat these as paired acceptance and refusal clauses. If fresh source inspection disproves either premise, revise the plan before implementation rather than adding a workaround.

#### Commit, restore, and command path

Start from the owner named above. Validate IDs and phase against that owner, execute one domain command, and let that owner publish the resulting state. The presentation route may request, preview, confirm, cancel, and render; it cannot create a substitute state or compute a different outcome. No shadow inventory, hypothetical mutation, cloned simulator, or local what-if counter. Compare actions only with a pure owner preview. Before commit, preview and dialog state are disposable. After commit, duplicate callbacks resolve to the same result and cannot emit another reward, relation change, unlock, phase transition, or resource mutation. Restore rehydrates existing facts and is never a new command.

#### Data, save, determinism, and accessibility

Resolve authored IDs through the current catalog and validate references with the integrity path. Capture and restore through the actual owner; do not infer a new save section. Repeat identical inputs under the existing seeded contract and keep ordering stable. The interface identifies unavailable or stale information honestly and preserves close/back, focus, refresh, and disposal behavior.

#### Player-visible acceptance statements

- Preview reads same state as canonical action preflight; accept executes that command once; cancel is neutral.
- Unpreviewable action is an unavailable row or destination link, not fabricated success/cost/certainty.
- The selected command and affected target are visible before confirmation; the result is read back from its owner afterward.
- Cancel, close, back, invalid input, and stale preview leave the domain unchanged.
- Save/load preserves the result without replaying a side effect.
- Missing authoritative data displays unavailable/unknown instead of an approximation stored in a panel.

1. A reachable current source/command invokes the named owner, and the player can observe the resulting state. 2. ## 10. Cross-feature acceptance

All three subfeatures must agree on the same identity, source, and commit boundary. A refusal in one cannot partially commit another. Shared inputs are sampled once where the existing API requires a snapshot. The host route has one observable success path and one neutral rejection path; save round-trip preserves that outcome.

## 11. Stop conditions

- A supposed source or route is only a static registry label and has no reachable runtime consumer.
- A second component must own a copy of IDs, thresholds, unlocks, or resolved choices for the result to work.
- The save path cannot represent state under a current owner and no architecture decision is signed.
- A proposed result conflicts with current behavior or an active file claim.
- A view would present neutral, stale, projected, or missing data as observed certainty.
