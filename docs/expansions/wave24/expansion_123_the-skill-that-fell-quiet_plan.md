# EXPANSION 123 — The Skill That Fell Quiet

## Turn persisted skill atrophy into an understandable, bounded effect at the real medical and crafting decision points.

## Wave 24: A Feature at Its Owner

## Planning status

**Key feature:** Atrophy that affects work without taking away control  
**Classification:** Code-backed gameplay-effect gap  
**Anchor:** SkillAtrophySystem plus SurvivorSocialCoordinator  
**Artifact:** evidence-grounded design plan only; no production code or gameplay data changed.

## 1. Expansion thesis

The game already tracks consecutive low-morale days, records permanent medical and crafting atrophy, saves it through the survivor-social owner, and exposes an atrophy read model. The declared 0.5 multiplier has no located consumer in current medical or crafting checks. This feature makes the consequence truthful: warn while change is avoidable, apply the existing bounded rule at a canonical action, and explain why its outcome differs.

## 2. Player value and scope

This plan centers one player-facing capability and divides it into exactly three unique subfeatures. They are distinct acceptance boundaries of the same key feature, not unrelated expansions. Working behavior is named and preserved. A missing path is called missing only where current source review supports the claim; an extension is labeled as an extension. The casebooks below are proposed checks, not existing or passing tests.

## 4. Player-facing contract

The promise is **Atrophy that affects work without taking away control**. The feature is integrated only when its current owner, command or event source, persistence where needed, and observable player result agree. This document does not authorize a parallel mutable authority.

## 5. Decision gate

Keep the existing permanence and 0.5 value unless a signed balance decision changes them. Do not add recovery, stack another morale debuff, or create a second skill cache. Any change to permanence requires a separate design approval.

## 6. Explicit exclusions

- No new skill catalog, progression ledger, morale threshold, random decay, role prohibition, or irreversible loss of item recipes.
- No blanket output reduction: only medical and crafting skill inputs explicitly named by SkillAtrophySystem may be affected.
- No UI-only penalty that does not change the canonical action; no Core decision derived from a Godot panel.

## 7. Dependency-ordered implementation sequence

1. Map actual medical and crafting skill reads from command preflight through committed result and identify canonical owner seams.
2. Specify how existing atrophy modifies one effective input and is displayed; use the existing 0.5 constant once.
3. Bind the warning countdown to the existing low-morale streak without a duplicate saved counter.
4. Verify save/load, exact threshold, invalid actors, and unchanged outcomes for other skills.

## 8. Shared invariants

1. One authority owns every mutable fact. Core computes; host adapts; Godot panels issue existing commands and display truthful state.
2. JSON is the authority for authored IDs, conditions, strings, and thresholds. A declaration or scanner entry is evidence to verify, not proof of player reachability.
3. Persist through the actual save-section owner. Restore rehydrates facts without replaying actions or side effects; absent legacy fields use the existing neutral/default contract.
4. Deterministic behavior uses current seeded inputs and stable ordering. Never use wall-clock time, unseeded randomness, or UI callbacks to own a gameplay choice.
5. Every refusal is neutral and visible: stale preview, invalid ID, wrong phase, absent owner, canceled dialog, and unavailable data cannot silently commit.
6. Do not build parallel caches for facts already represented by the named system. Derived display values are recomputed from the owner.
7. Voluntary actions remain voluntary unless current contract already defines automatic behavior. Forecasts retain uncertainty and source attribution.
8. Implementation requires a fresh premise audit, exact file claim, focused verification, save review, and closeout in the current project ledger.

## 9. Three unique subfeatures

The following three sections are the complete decomposition of the key feature. Each has its own promise, owner boundary, refusal contract, and verification casebook.

### Subfeature 1 — A Countdown the Survivor Can Understand

**Player promise:** Before day fourteen, the player sees a defined skill risk approaching and the existing morale state driving it.  
**Owner:** `SkillAtrophySystem.consecutiveLowMoraleDays and SurvivorSocialCoordinator read model; the panel is presentation only.`  
**State contract:** The streak already persists inside SurvivorSocialSaveState.atrophy. Compute remaining time from it; do not save a duplicate countdown.  
**Presentation boundary:** Survivor detail/social panel with per-survivor source, elapsed low-morale time, and affected skills; preserve lifecycle/focus.

#### Evidence-to-contract reading

At 13 days the view reports the remaining window; at 14 the owner records atrophy; morale at or above 20 resets only the unfinished danger streak as currently defined. Unknown/dead survivor, missing social model, non-finite duration, or stale view displays unavailable rather than false precision. Treat these as paired acceptance and refusal clauses. If fresh source inspection disproves either premise, revise the plan before implementation rather than adding a workaround.

#### Commit, restore, and command path

Start from the owner named above. Validate IDs and phase against that owner, execute one domain command, and let that owner publish the resulting state. The presentation route may request, preview, confirm, cancel, and render; it cannot create a substitute state or compute a different outcome. The streak already persists inside SurvivorSocialSaveState.atrophy. Compute remaining time from it; do not save a duplicate countdown. Before commit, preview and dialog state are disposable. After commit, duplicate callbacks resolve to the same result and cannot emit another reward, relation change, unlock, phase transition, or resource mutation. Restore rehydrates existing facts and is never a new command.

#### Data, save, determinism, and accessibility

Resolve authored IDs through the current catalog and validate references with the integrity path. Capture and restore through the actual owner; do not infer a new save section. Repeat identical inputs under the existing seeded contract and keep ordering stable. The interface identifies unavailable or stale information honestly and preserves close/back, focus, refresh, and disposal behavior.

#### Player-visible acceptance statements

- At 13 days the view reports the remaining window; at 14 the owner records atrophy; morale at or above 20 resets only the unfinished danger streak as currently defined.
- Unknown/dead survivor, missing social model, non-finite duration, or stale view displays unavailable rather than false precision.
- The selected command and affected target are visible before confirmation; the result is read back from its owner afterward.
- Cancel, close, back, invalid input, and stale preview leave the domain unchanged.
- Save/load preserves the result without replaying a side effect.
- Missing authoritative data displays unavailable/unknown instead of an approximation stored in a panel.
