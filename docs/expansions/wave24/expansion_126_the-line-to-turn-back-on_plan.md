# EXPANSION 126 — The Line to Turn Back On

## Let players set an expedition-specific return policy that extends existing three-tick auto-return and explicit push-luck choice.

## Wave 24: A Feature at Its Owner

## Planning status

**Key feature:** Player-set expedition return limits  
**Classification:** Live-system extension  
**Anchor:** ExpeditionSystem active state, estimates, phase changes, retreat, and ExpeditionHostSession  
**Artifact:** evidence-grounded design plan only; no production code or gameplay data changed.

## 1. Expansion thesis

Expeditions already support explicit retreat and automatic return after three looting ticks; player can opt into push-luck to bypass the automatic cap. This extension adds optional per-sortie limits understandable before dispatch, names why a boundary triggers, and lets the player override through an explicit reversible choice. Existing three-tick behavior remains the default.

## 2. Player value and scope

This plan centers one player-facing capability and divides it into exactly three unique subfeatures. They are distinct acceptance boundaries of the same key feature, not unrelated expansions. Working behavior is named and preserved. A missing path is called missing only where current source review supports the claim; an extension is labeled as an extension. The casebooks below are proposed checks, not existing or passing tests.

## 4. Player-facing contract

The promise is **Player-set expedition return limits**. The feature is integrated only when its current owner, command or event source, persistence where needed, and observable player result agree. This document does not authorize a parallel mutable authority.

## 5. Decision gate

Preserve default and push-luck semantics. New limits must use verified estimate/runtime values and live on the sortie state only if that contract is accepted. No separate manager, wall-clock timing, or change to the existing permitted phase for manual retreat.

## 6. Explicit exclusions

- Do not claim manual or automatic retreat is missing.
- No forced rescue, casualty system, background AI, global campaign policy, or hidden dispatch cancellation.
- No duplicate expedition store, random threshold selection, or panel-owned phase transition.

## 7. Dependency-ordered implementation sequence

1. Map fields available in preview/estimate/active state; separate projections from observations.
2. Specify version-safe optional per-sortie policy; absent legacy value equals current three-tick behavior.
3. Evaluate policy only at existing safe checkpoint and transition through ExpeditionSystem.
4. Expose reason, preview, override, persistence, and cancellation through current session/panel; verify old saves and push-luck parity.

## 8. Shared invariants

1. One authority owns every mutable fact. Core computes; host adapts; Godot panels issue existing commands and display truthful state.
2. JSON is the authority for authored IDs, conditions, strings, and thresholds. A declaration or scanner entry is evidence to verify, not proof of player reachability.
3. Persist through the actual save-section owner. Restore rehydrates facts without replaying actions or side effects; absent legacy fields use the existing neutral/default contract.
4. Deterministic behavior uses current seeded inputs and stable ordering. Never use wall-clock time, unseeded randomness, or UI callbacks to own a gameplay choice.
5. Every refusal is neutral and visible: stale preview, invalid ID, wrong phase, absent owner, canceled dialog, and unavailable data cannot silently commit.
6. Do not build parallel caches for facts already represented by the named system. Derived display values are recomputed from the owner.
7. Voluntary actions remain voluntary unless current contract already defines automatic behavior. Forecasts retain uncertainty and source attribution.
8. Implementation requires a fresh premise audit, exact file claim, focused verification, save review, and closeout in the current project ledger.

## 9. Three unique subfeatures

The following three sections are the complete decomposition of the key feature. Each has its own promise, owner boundary, refusal contract, and verification casebook.

### Subfeature 1 — Choose the Return Line Before Dispatch

**Player promise:** For one sortie, player may keep the default or select supported limits and see their predicted effect before start.  
**Owner:** `ExpeditionSystem PreviewStart/Estimate and selected ExpeditionState; panel edits only through host commands.`  
**State contract:** Policy is per sortie. Use only verified fields such as loot cap, travel estimate, stamina, capacity, or supported breakdown inputs; unknown fields stay unavailable.  
**Presentation boundary:** Dispatch panel beside current route estimate; default preserves three-tick automatic return.

#### Evidence-to-contract reading

Validated policy is copied at dispatch, consumed by both estimate and runtime, and cannot mutate another trip. Invalid threshold, unavailable projection, canceled preview, or changed route/version rejects start without active state. Treat these as paired acceptance and refusal clauses. If fresh source inspection disproves either premise, revise the plan before implementation rather than adding a workaround.

#### Commit, restore, and command path

Start from the owner named above. Validate IDs and phase against that owner, execute one domain command, and let that owner publish the resulting state. The presentation route may request, preview, confirm, cancel, and render; it cannot create a substitute state or compute a different outcome. Policy is per sortie. Use only verified fields such as loot cap, travel estimate, stamina, capacity, or supported breakdown inputs; unknown fields stay unavailable. Before commit, preview and dialog state are disposable. After commit, duplicate callbacks resolve to the same result and cannot emit another reward, relation change, unlock, phase transition, or resource mutation. Restore rehydrates existing facts and is never a new command.

#### Data, save, determinism, and accessibility

Resolve authored IDs through the current catalog and validate references with the integrity path. Capture and restore through the actual owner; do not infer a new save section. Repeat identical inputs under the existing seeded contract and keep ordering stable. The interface identifies unavailable or stale information honestly and preserves close/back, focus, refresh, and disposal behavior.

#### Player-visible acceptance statements

- Validated policy is copied at dispatch, consumed by both estimate and runtime, and cannot mutate another trip.
- Invalid threshold, unavailable projection, canceled preview, or changed route/version rejects start without active state.
- The selected command and affected target are visible before confirmation; the result is read back from its owner afterward.
- Cancel, close, back, invalid input, and stale preview leave the domain unchanged.
- Save/load preserves the result without replaying a side effect.
- Missing authoritative data displays unavailable/unknown instead of an approximation stored in a panel.

## 10. Cross-feature acceptance

All three subfeatures must agree on the same identity, source, and commit boundary. A refusal in one cannot partially commit another. Shared inputs are sampled once where the existing API requires a snapshot. The host route has one observable success path and one neutral rejection path; save round-trip preserves that outcome.

## 11. Stop conditions

- A supposed source or route is only a static registry label and has no reachable runtime consumer.
- A second component must own a copy of IDs, thresholds, unlocks, or resolved choices for the result to work.
- The save path cannot represent state under a current owner and no architecture decision is signed.
- A proposed result conflicts with current behavior or an active file claim.
- A view would present neutral, stale, projected, or missing data as observed certainty.
- A restore, retry, or presentation refresh emits a gameplay effect.
