# EXPANSION 124 — A Name for What Came Back

## Bring the unused trophy-award ledger and live quarry-preservation path under one exactly-once, provenance-aware contract.

## Wave 24: A Feature at Its Owner

## Planning status

**Key feature:** One trophy opportunity from preserved quarry to shelter display  
**Classification:** Partial integration and authority-convergence gap  
**Anchor:** TrophySystem, WildlifeTrappingSystem, CraftingSystem, and ShelterDecorSystem  
**Artifact:** evidence-grounded design plan only; no production code or gameplay data changed.

## 1. Expansion thesis

A rare quarry trophy is already craftable and the shelter already has trophy slots. The opportunity is one authoritative journey. Core has a persistent TrophySystem with eligibility, award, and recipe APIs; live trapping keeps its own recipe mapping and trophy-ready event. Connect one owner through preservation, unlock, craft, display, and morale without duplicate records or double rewards.

## 2. Player value and scope

This plan centers one player-facing capability and divides it into exactly three unique subfeatures. They are distinct acceptance boundaries of the same key feature, not unrelated expansions. Working behavior is named and preserved. A missing path is called missing only where current source review supports the claim; an extension is labeled as an extension. The casebooks below are proposed checks, not existing or passing tests.

## 4. Player-facing contract

The promise is **One trophy opportunity from preserved quarry to shelter display**. The feature is integrated only when its current owner, command or event source, persistence where needed, and observable player result agree. This document does not authorize a parallel mutable authority.

## 5. Decision gate

Before implementation, decide which current save owner owns award/unlock state. Extend an existing shelter/crafting lifecycle envelope only if it actually owns those facts; otherwise seek an explicit architecture decision. Never keep the trap map and TrophySystem catalog as parallel mutable authorities.

## 6. Explicit exclusions

- No new trophy item families, hunting minigame, duplicate morale reward, independent species map, award store, decor ledger, or copy of recipe unlock state.
- Do not claim trapping, trophy crafting, or shelf placement is missing; each has current source evidence.
- An award may come only from existing successful preservation. Do not add kill counts, specimen extraction, or unverified species.

## 7. Dependency-ordered implementation sequence

1. Compare trophies.json, recipes/items, trapping species map, and display classification row-by-row.
2. Select one species-eligibility authority and name the save owner before wiring calls.
3. Route successful preservation once to the award authority, then use existing crafting/decor owners.
4. Verify no award, unlock, or morale event replays on restore and legacy mounted items still load.

## 8. Shared invariants

1. One authority owns every mutable fact. Core computes; host adapts; Godot panels issue existing commands and display truthful state.
2. JSON is the authority for authored IDs, conditions, strings, and thresholds. A declaration or scanner entry is evidence to verify, not proof of player reachability.
3. Persist through the actual save-section owner. Restore rehydrates facts without replaying actions or side effects; absent legacy fields use the existing neutral/default contract.
4. Deterministic behavior uses current seeded inputs and stable ordering. Never use wall-clock time, unseeded randomness, or UI callbacks to own a gameplay choice.
5. Every refusal is neutral and visible: stale preview, invalid ID, wrong phase, absent owner, canceled dialog, and unavailable data cannot silently commit.
6. Do not build parallel caches for facts already represented by the named system. Derived display values are recomputed from the owner.
7. Voluntary actions remain voluntary unless current contract already defines automatic behavior. Forecasts retain uncertainty and source attribution.
8. Implementation requires a fresh premise audit, exact file claim, focused verification, save review, and closeout in the current project ledger.

## 9. Three unique subfeatures

The following three sections are the complete decomposition of the key feature. Each has its own promise, owner boundary, refusal contract, and verification casebook.

### Subfeature 1 — Preservation Creates One Eligible Opportunity

**Player promise:** Only a successful preserved quarry result for a catalog-listed species can create the trophy opportunity.  
**Owner:** `Actual trapping preservation event as input; TrophySystem is the proposed single eligibility authority after owner decision.`  
**State contract:** Do not infer an eligible trophy from a kill, caught-but-unpreserved animal, or unrelated species event. Trap state owns success.  
**Presentation boundary:** Concise result on existing trapping/decor route; no new animal identity ledger.

#### Evidence-to-contract reading

Input resolves through one canonical species record and produces one TrophyAwardRecord or no trophy event. Unknown species, missing definition, failed preservation, empty recipe, or repeated event yields no second award or display side effect. Treat these as paired acceptance and refusal clauses. If fresh source inspection disproves either premise, revise the plan before implementation rather than adding a workaround.

#### Commit, restore, and command path

Start from the owner named above. Validate IDs and phase against that owner, execute one domain command, and let that owner publish the resulting state. The presentation route may request, preview, confirm, cancel, and render; it cannot create a substitute state or compute a different outcome. Do not infer an eligible trophy from a kill, caught-but-unpreserved animal, or unrelated species event. Trap state owns success. Before commit, preview and dialog state are disposable. After commit, duplicate callbacks resolve to the same result and cannot emit another reward, relation change, unlock, phase transition, or resource mutation. Restore rehydrates existing facts and is never a new command.

#### Data, save, determinism, and accessibility

Resolve authored IDs through the current catalog and validate references with the integrity path. Capture and restore through the actual owner; do not infer a new save section. Repeat identical inputs under the existing seeded contract and keep ordering stable. The interface identifies unavailable or stale information honestly and preserves close/back, focus, refresh, and disposal behavior.

#### Player-visible acceptance statements

- Input resolves through one canonical species record and produces one TrophyAwardRecord or no trophy event.
- Unknown species, missing definition, failed preservation, empty recipe, or repeated event yields no second award or display side effect.
- The selected command and affected target are visible before confirmation; the result is read back from its owner afterward.
- Cancel, close, back, invalid input, and stale preview leave the domain unchanged.
- Save/load preserves the result without replaying a side effect.
- Missing authoritative data displays unavailable/unknown instead of an approximation stored in a panel.

Start from the owner named above. Validate IDs and phase against that owner, execute one domain command, and let that owner publish the resulting state. After commit, duplicate callbacks resolve to the same result and cannot emit another reward, relation change, unlock, phase transition, or resource mutation. Restore rehydrates existing facts and is never a new command.

#### Data, save, determinism, and accessibility

Resolve authored IDs through the current catalog and validate references with the integrity path. Capture and restore through the actual owner; do not infer a new save section. Repeat identical inputs under the existing seeded contract and keep ordering stable. The interface identifies unavailable or stale information honestly and preserves close/back, focus, refresh, and disposal behavior.

1. A reachable current source/command invokes the named owner, and the player can observe the resulting state. 2. Focused checks cover owner state, refusal, save/restore, duplicate delivery, and route lifecycle. 3. Fresh source evidence is recorded for any premise correction. 4. ## 10. Cross-feature acceptance

All three subfeatures must agree on the same identity, source, and commit boundary. A refusal in one cannot partially commit another. Shared inputs are sampled once where the existing API requires a snapshot. The host route has one observable success path and one neutral rejection path; save round-trip preserves that outcome.

## 11. Stop conditions

- A supposed source or route is only a static registry label and has no reachable runtime consumer.
- A second component must own a copy of IDs, thresholds, unlocks, or resolved choices for the result to work.
- The save path cannot represent state under a current owner and no architecture decision is signed.
- A proposed result conflicts with current behavior or an active file claim.
