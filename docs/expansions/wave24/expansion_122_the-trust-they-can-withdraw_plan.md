# EXPANSION 122 — The Trust They Can Withdraw

## A private confession route that earns disclosure, lets the player choose an audience, and keeps resolved choices from leaking or replaying.

## Wave 24: A Feature at Its Owner

## Planning status

**Key feature:** Consent-first confession resolution  
**Classification:** Code-backed route and persistence gap  
**Anchor:** ConfessionSecretSystem plus confession_secrets.json  
**Artifact:** evidence-grounded design plan only; no production code or gameplay data changed.

## 1. Expansion thesis

Ashfall already has a Core catalog and deterministic secret-resolution methods. The player-facing bridge is the missing promise: disclosure must be offered without extraction, its audience must stay bounded by authored facts and participant consent, and consequences must travel through existing relationship, guilt, moral, and faction owners exactly once. This is one feature about who controls private knowledge.

## 2. Player value and scope

This plan centers one player-facing capability and divides it into exactly three unique subfeatures. They are distinct acceptance boundaries of the same key feature, not unrelated expansions. Working behavior is named and preserved. A missing path is called missing only where current source review supports the claim; an extension is labeled as an extension. The casebooks below are proposed checks, not existing or passing tests.

## 6. Explicit exclusions

- No free-text confession authoring, surveillance mechanic, mind-reading, compelled interrogation, public rumor broadcast, new moral-alignment meter, duplicated relationship ledger, or new faction-standing authority.
- No secret is discovered merely because a UI page opens. Existing authored discovery_path and current event evidence remain eligible triggers.
- Do not reopen HiddenAgendaSystem, PersonalLetterProjection, moral-choice catalog, or rumor ownership; route only facts supported by this catalog and system.

## 7. Dependency-ordered implementation sequence

1. Confirm the content source and host route from current files; scanner mappings are hints, not proof.
2. Resolve the correct save owner and backward-compatibility contract before adding a runtime call.
3. Wire consent prompt and accepted resolution through existing system methods; keep presentation free of domain decisions.
4. Verify refusal, single-fire events, restore parity, accessible navigation, and effect ownership with focused tests before declaring completion.

## 8. Shared invariants

1. One authority owns every mutable fact. Core computes; host adapts; Godot panels issue existing commands and display truthful state.
2. JSON is the authority for authored IDs, conditions, strings, and thresholds. A declaration or scanner entry is evidence to verify, not proof of player reachability.
3. Persist through the actual save-section owner. Restore rehydrates facts without replaying actions or side effects; absent legacy fields use the existing neutral/default contract.
4. Deterministic behavior uses current seeded inputs and stable ordering. Never use wall-clock time, unseeded randomness, or UI callbacks to own a gameplay choice.
5. Every refusal is neutral and visible: stale preview, invalid ID, wrong phase, absent owner, canceled dialog, and unavailable data cannot silently commit.
6. Do not build parallel caches for facts already represented by the named system. Derived display values are recomputed from the owner.
7. Voluntary actions remain voluntary unless current contract already defines automatic behavior. Forecasts retain uncertainty and source attribution.
8. Implementation requires a fresh premise audit, exact file claim, focused verification, save review, and closeout in the current project ledger.

## 9. Three unique subfeatures

The following three sections are the complete decomposition of the key feature. Each has its own promise, owner boundary, refusal contract, and verification casebook.

### Subfeature 1 — An Invitation With a Plain Decline

**Player promise:** The player encounters a secret only through a supported authored source, hears what disclosure asks of them, and can leave without extracting or resolving it.  
**Owner:** `ConfessionSecretSystem.DiscoverSecret and the current owning narrative/quest route; authored facts remain in ConfessionSecretCatalog.`  
**State contract:** Discovery is already represented by discoveredSecretIds. Decline must not mark the secret discovered, resolved, or public. Persist a refusal only if a named owner and explicit save contract are approved.  
**Presentation boundary:** A bounded conversation or record route launched by its actual source; no always-on private dossier.

#### Evidence-to-contract reading

Only a catalog-valid secret with verified source context can be offered. Acceptance calls the existing discovery API once; decline leaves secret state and all effect owners unchanged. Unknown ID, missing subject, stale source, absent route context, or cancelled prompt returns neutrally with no hidden write. Treat these as paired acceptance and refusal clauses. If fresh source inspection disproves either premise, revise the plan before implementation rather than adding a workaround.

#### Commit, restore, and command path

Start from the owner named above. Validate IDs and phase against that owner, execute one domain command, and let that owner publish the resulting state. The presentation route may request, preview, confirm, cancel, and render; it cannot create a substitute state or compute a different outcome. Discovery is already represented by discoveredSecretIds. Decline must not mark the secret discovered, resolved, or public. Persist a refusal only if a named owner and explicit save contract are approved. Before commit, preview and dialog state are disposable. After commit, duplicate callbacks resolve to the same result and cannot emit another reward, relation change, unlock, phase transition, or resource mutation. Restore rehydrates existing facts and is never a new command.

#### Data, save, determinism, and accessibility

Resolve authored IDs through the current catalog and validate references with the integrity path. Capture and restore through the actual owner; do not infer a new save section. Repeat identical inputs under the existing seeded contract and keep ordering stable. The interface identifies unavailable or stale information honestly and preserves close/back, focus, refresh, and disposal behavior.

#### Player-visible acceptance statements

- Only a catalog-valid secret with verified source context can be offered. Acceptance calls the existing discovery API once; decline leaves secret state and all effect owners unchanged.
- Unknown ID, missing subject, stale source, absent route context, or cancelled prompt returns neutrally with no hidden write.
- The selected command and affected target are visible before confirmation; the result is read back from its owner afterward.
- Cancel, close, back, invalid input, and stale preview leave the domain unchanged.
- Save/load preserves the result without replaying a side effect.
- Missing authoritative data displays unavailable/unknown instead of an approximation stored in a panel.

**State contract:** SecretChoiceRecord stores selected choice and day. It does not authorize arbitrary audience lists, public broadcast, or a second relationship history.

A confirmed choice calls exactly one existing method with IDs sourced from the current entry and route. Cancel is neutral; the panel cannot substitute a target. Treat these as paired acceptance and refusal clauses. If fresh source inspection disproves either premise, revise the plan before implementation rather than adding a workaround.

#### Commit, restore, and command path

Start from the owner named above. Validate IDs and phase against that owner, execute one domain command, and let that owner publish the resulting state. The presentation route may request, preview, confirm, cancel, and render; it cannot create a substitute state or compute a different outcome. SecretChoiceRecord stores selected choice and day. It does not authorize arbitrary audience lists, public broadcast, or a second relationship history. Before commit, preview and dialog state are disposable. After commit, duplicate callbacks resolve to the same result and cannot emit another reward, relation change, unlock, phase transition, or resource mutation. Restore rehydrates existing facts and is never a new command.

#### Data, save, determinism, and accessibility

Resolve authored IDs through the current catalog and validate references with the integrity path. Capture and restore through the actual owner; do not infer a new save section. Repeat identical inputs under the existing seeded contract and keep ordering stable. The interface identifies unavailable or stale information honestly and preserves close/back, focus, refresh, and disposal behavior.
