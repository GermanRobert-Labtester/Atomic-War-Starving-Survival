## 9. Exactly three subfeatures

### 1. One confirmed incident, one truthful alert

Define the evidence threshold and stable source identity before an alert enters the persistent list. Coalesce repeated observations of the same unresolved incident; never turn a transient presentation refresh into a new alert. Authority boundary: The producing hazard system remains authoritative for incident facts; EmergencyAlertSystem may own an actionable projection only after an explicit producer contract is approved.

### 2. Protocol intent with observable execution

Present protocol choices as commands that existing response owners can accept or refuse. An activated protocol is intent plus status, not proof that evacuees moved, supplies were staged, or a hazard was contained. Authority boundary: EmergencyAlertSystem owns protocol records and their lifecycle; response execution remains with the current evacuation, shelter, roster, or hazard command owners.

### 3. Close the loop and preserve the record

Separate acknowledgement, escalation, source repair, alert resolution and archive retention. Offer a quiet history that tells the player what changed and which owner confirmed it. Authority boundary: EmergencyAlertSystem owns its alert state; the originating subsystem alone confirms source repair; existing campaign history/save owners determine retention and export.

## 10. State and command contract

1. One confirmed incident, one truthful alert: use stable IDs, validate against the current source owner immediately before commit, make repeated UI delivery idempotent where the domain permits, and return an explicit accepted/refused/stale outcome. Required visible postcondition: one source incident maps to at most one open alert under the approved identity contract; resolved history stays historical and a distinct incident remains distinguishable. Forbidden shortcut: The current RaiseAlert creates a new sequence for every invocation. It has no source-key coalescing in the inspected implementation, so producers must not be wired until duplicate semantics are resolved.

2. Protocol intent with observable execution: use stable IDs, validate against the current source owner immediately before commit, make repeated UI delivery idempotent where the domain permits, and return an explicit accepted/refused/stale outcome. Required visible postcondition: the protocol state records request, accepted/refused/pending status and actual result separately; no fake completion toast is shown. Forbidden shortcut: ActivateProtocol cannot become a generic callback that bypasses action owners. Existing crisis navigation remains a read/route surface and is not silently repurposed as execution.

3. Close the loop and preserve the record: use stable IDs, validate against the current source owner immediately before commit, make repeated UI delivery idempotent where the domain permits, and return an explicit accepted/refused/stale outcome. Required visible postcondition: resolution has a source-confirmed reason and timestamp; acknowledgement never clears the source, escalation is visible, and archive records cannot be edited from a read-only history surface. Forbidden shortcut: Alert dismissal is not source repair, and a resolved alert is not a campaign victory. Retention limits require an explicit policy rather than silent truncation.
