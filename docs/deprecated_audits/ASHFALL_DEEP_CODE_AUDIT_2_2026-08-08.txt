  SetHealth where health ≤ 0 must also trigger the OnDied chain. The editor
  gate can grep for `SetHealth.*0f` and ensure the call site also has an
  `OnDied` invocation within 3 lines.

[DEATH-004]  Severity: HIGH  |  Type: zombie state
  Location:      SurvivorNeedWrite.cs SetHealth (line 21) — no !IsAlive guard
  Description:   SetHealth(sv, health) has no `if (!sv.IsAlive) return;` check.
  If a system accidentally calls SetHealth on a dead survivor with health > 0,
  the survivor gets positive HP but stays dead (State = Dead, with Health = 50f).
  This "zombie" state is written to the save file and looks alive to polling
  systems. Only one path legitimately writes Health on a dead survivor:
  MedicalPerkSystem.TryAdministerAdrenaline (line 423), which immediately sets
  State = Idle afterwards. Every other call site either uses AdjustHealth (which
  DOES have `!sv.IsAlive`), or SetHealth on a known-alive survivor.

    • LaborCampSystem.cs:117 — SetHealth(sv, 40f) on rescued laborer
    • ChildDependentSystem.cs:134 — SetHealth(Child, 80f) on reintegrated child
    • LightSystemHelper.cs:93 — SetHealth(sv, Mathf.Max(1f, ...))
    • PersonalQuestSystem.Ashes.cs:416, 579 — SetHealth on alpha/patient
    • PersonalQuestSystem.CivilWar.cs:381, 404, 406 — SetHealth on empath/patient
    • PersonalQuestSystem.cs:2647 — SetHealth on firefighter
    • BunkerSocialSystems.cs:667 — SetHealth(leader, 0f) ← kills already

  Of these, only leader=0f is a guaranteed kill. The others could theoretically
  be called on a dead survivor if the caller does not check IsAlive first.
  Suggested Fix: Add `if (!sv.IsAlive) return;` to SetHealth, AND add an
  explicit `SetHealthOnDead` overload for the adrenaline-revive path (with a
  clear name so the caller can't accidentally use it).
  Suggested Harden: Reflection test — find all SetHealth calls where the
  health arg is > 0 and the survivor arg is not guarded by IsAlive or State==Idle
  in the preceding 5 lines.

[MED-016]  Severity: MEDIUM  |  Type: incomplete treatment
  Location:      MedicalSystem.CompleteTreatment ~945-1015
  Description:   CompleteTreatment removes the affliction from the treatment list
  and fires OnAfflictionCured. However, if a survivor has multiple afflictions
  and one of them was being treated (active.IsTreating = true), removing it
  leaves the survivor with other afflictions that continue to progress. This is
  correct. BUT: if CompleteTreatment is called on a treatment that was halted
  (recipe.haltOnly), the affliction is NOT removed — only its progression is
  halted. This is also correct.

  The edge case: a survivor with Sepsis (fatal within X days) is being treated.
  The treatment timer expires successfully, CompleteTreatment fires, the
  affliction is removed, and health is restored. But if a SECOND affliction
  (e.g. bacterial_infection) was also active AND had a treatment in progress,
  that second treatment is still running. When it completes, the method finds
  active.AfflictionId in the list (it's still there) and removes it. This is
  correct — the two treatments are independent.

  However: if two medics are treating the SAME affliction (same afflictionId),
  the treatment list can have two entries for the same ID. When the first
  completes, it removes one entry. When the second completes, it also finds
  the second entry. This works. BUT: the `active.AfflictionId` removal at line
  975 is a List.Remove — it removes the FIRST matching entry, not necessarily
  the one the treatment was for. If two medics treat sepsis, medic A's treatment
  finishes first but removes medic B's active affliction entry, medic B's
  treatment hours remain non-zero but the affliction they were treating is
  already gone. This would be a no-op at worst (the affliction was already cured).
  Suggested Fix: Use reference removal (list.Remove(active)) instead of
  list.RemoveByPredicate(afflictionId). The treatment list holds ActiveAffliction
  objects — remove the exact object the treatment was for.
  Suggested Harden: Medical smoke test — two medics treat the same affliction
  on the same patient, tick both treatments to completion, assert the affliction
  is only cured once (no double-cure event).

[MED-017]  Severity: LOW  |  Type: missing event
  Location:      MedicalSystem line 423 — adrenaline revive sets State directly
  Description:   TryAdministerAdrenaline writes Health=1, State=Idle without
  firing OnNeedChanged for Health. The death-to-alive transition fires
  OnDeathsDoorRevived but does not notify systems that Health changed from 0 to 1.
  HUDs polling Health will eventually pick up the change on the next frame, but
  no event pushes it.
  Suggested Fix: Call _needs.Modify(survivor, Health, 1f) instead of direct
  Needs.Health = 1f, after setting State = Idle (so the survivor is alive
  when Modify runs its IsAlive guard).
